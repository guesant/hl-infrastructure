# Gateway API: GatewayClass, Gateway e HTTPRoute

O recurso `Ingress` original do Kubernetes tenta descrever, num único objeto, tanto a infraestrutura de borda (qual controlador atende, em qual porta, com qual certificado) quanto as regras de roteamento de uma aplicação específica (qual caminho ou qual host vai para qual `Service`). Essa mistura de responsabilidades força um compromisso: campos comuns o suficiente para caber em qualquer controlador, e qualquer coisa mais específica de um controlador (Traefik, Nginx, um provider de nuvem) precisa fugir para anotações num formato próprio de cada implementação, sem padronização nenhuma entre elas. A Gateway API é o sucessor desenhado para separar essas duas responsabilidades em recursos distintos, cada um pertencendo a quem realmente deveria controlá-lo.

Três tipos de recurso compõem o modelo. Um `GatewayClass`, de escopo de cluster e criado uma única vez, identifica qual controlador implementa aquela classe de gateway, análogo ao papel que uma `StorageClass` cumpre para armazenamento: ela não expõe porta nenhuma sozinha, só declara "isto aqui é atendido pelo Traefik" ou "isto aqui é atendido pelo Cilium". Um `Gateway` referencia essa classe e declara os pontos de entrada reais, um ou mais **listeners**, cada um com uma porta, um protocolo e, quando o protocolo é HTTPS, qual certificado TLS terminar a conexão; esse recurso pertence a quem administra a infraestrutura de rede do cluster, porque decidir em que porta e com qual certificado o tráfego externo entra é uma decisão de plataforma, não de uma aplicação individual. Uma `HTTPRoute` referencia um `Gateway` (ou um listener específico dele) e declara as regras de roteamento propriamente ditas, quais hostnames ela atende e para qual `Service` encaminhar; esse recurso pertence a quem opera a aplicação, e pode viver no mesmo namespace dela, em vez de precisar editar um objeto compartilhado de infraestrutura toda vez que uma rota nova precisa existir.

Essa separação de posse é o ganho estrutural central: com o `Ingress` clássico, adicionar uma rota para uma aplicação nova frequentemente significava editar o mesmo objeto ou reaproveitar anotações específicas do controlador; com a Gateway API, o time de infraestrutura declara o `Gateway` uma vez, e cada equipe de aplicação declara sua própria `HTTPRoute` de forma independente, sem tocar no recurso compartilhado. Um `Gateway` controla quem pode fazer isso através de `allowedRoutes`: permitir rotas de qualquer namespace (`from: All`) favorece a conveniência de cada aplicação morar ao lado do serviço que expõe, enquanto restringir a rotas do mesmo namespace do `Gateway`, ou a uma seleção por label, favorece um controle mais estrito de quem pode publicar tráfego através daquele ponto de entrada. Quando um `Gateway` declara mais de um listener (um típico exemplo sendo um `web` na porta 80 que só redireciona para HTTPS, e um `websecure` na porta 443 que efetivamente termina TLS), uma `HTTPRoute` pode se associar a todos eles ou apontar para um listener específico através de `sectionName`, o que importa sobretudo quando o `Gateway` referenciado vive num namespace diferente do da rota, caso em que declarar o namespace de destino explicitamente deixa de ser opcional.

A padronização também é o que torna o `GatewayClass` trocável sem reescrever o resto: como toda `HTTPRoute` fala o mesmo formato independente de qual controlador está por trás, migrar de uma implementação para outra (de um projeto como o Traefik para outro como o próprio Cilium, quando ambos implementam a especificação) é, em princípio, uma questão de trocar o `GatewayClass` referenciado, não de reescrever cada regra de roteamento de cada aplicação num formato de anotação novo. Na prática, funcionalidades que a especificação ainda não padronizou, como autenticação na borda de uma requisição, continuam exigindo um recurso específico do controlador (um `Middleware` do Traefik, por exemplo) referenciado a partir de uma `HTTPRoute` por uma extensão prevista pela própria especificação para esse fim, o que preserva a maior parte da portabilidade sem fingir que toda funcionalidade possível já tem um equivalente padrão.
