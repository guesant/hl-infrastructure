# Smoke test e o limite da automação de checklist

Um smoke test é uma verificação rápida e deliberadamente rasa, pensada para responder a uma pergunta bem mais estreita do que "está tudo certo": o ambiente está minimamente acessível e vivo o suficiente para justificar investir tempo num diagnóstico mais profundo? Um exemplo típico confirma que as ferramentas de linha de comando necessárias existem, que a API do que está sendo verificado responde, que os nós ou processos esperados estão no estado básico correto, nada além disso. Tratar um smoke test como prova de prontidão é o erro mais comum dessa prática: ele não confirma que RBAC está correto, que probes estão bem configuradas, ou que um backup realmente restaura, só que o sistema não está numa falha óbvia e imediata que tornaria qualquer diagnóstico mais fino uma perda de tempo. O valor está exatamente nessa modéstia deliberada de escopo, ele roda em segundos e serve como filtro antes de um diagnóstico caro, não como substituto dele.

## Saída estruturada para automação, legível para humano

Um script de verificação que só imprime texto solto obriga quem o consome (uma pessoa ou outra automação) a interpretar a saída de novo a cada execução, sem garantia de que o formato continue igual na próxima versão. Um formato estruturado (um objeto com um carimbo de tempo, um resumo agregado de quantos itens passaram e falharam, e uma lista detalhada por item verificado, cada um com nome, estado e uma mensagem) resolve isso ao separar duas responsabilidades que normalmente se misturam: uma saída legível por humano no terminal, formatada para leitura rápida enquanto o comando roda, e um relatório estruturado (JSON é a escolha mais comum, por ser consumível por praticamente qualquer linguagem ou ferramenta sem um parser dedicado) emitido ao final, pronto para ser arquivado, comparado entre execuções, ou processado por outra automação sem exigir que ela reimplemente a lógica de interpretar texto livre.

## Nem todo item de um checklist é automatizável

A tentação de transformar cada item de um checklist operacional numa função automatizada esbarra num limite real: um item automatizável precisa produzir um sinal objetivo (zero linhas de saída, um valor exato esperado, um código de saída específico), e nem todo item de um checklist de operação satisfaz isso. Confirmar que uma porta está fechada, que uma tag de imagem não é flutuante, ou que um serviço reporta um estado específico são exemplos de verificações objetivas, direto candidatas a virar uma função de script. Confirmar que existe um responsável de escalonamento definido, que uma decisão de trade-off foi documentada, ou que alguém revisou um plano de rollback antes de aplicá-lo são itens que dependem de julgamento humano ou de um processo organizacional, sem um comando de verificação que produza `pass`/`fail` com sentido real; forçar esse tipo de item a virar uma função automatizada produz uma automação que sempre retorna sucesso, ou que falha por um motivo que não corresponde ao que o item realmente pretendia verificar. Tratar esses dois tipos de item de forma diferente, automatizando um e mantendo o outro como uma etapa manual explícita, é mais honesto do que fingir que todo o checklist virou código.

## Nunca esconder o comando por trás de uma verificação

Uma camada de conveniência sobre comandos já existentes (um script, uma CLI própria, uma automação de diagnóstico) corre um risco específico: quem usa a camada de conveniência aprende a rodar o atalho, mas nunca aprende o comando real por trás dele, o que se torna um problema no dia em que a conveniência não está disponível (um script que não roda naquele ambiente, uma ferramenta que não foi instalada) e ninguém lembra o comando original que ela substituía. A mitigação estrutural para isso é simples e vale para qualquer ferramenta desse tipo: cada verificação ou atalho deveria mostrar explicitamente o comando real que executou por trás, não só o resultado, mantendo a ferramenta subjacente como conhecimento acessível em vez de escondido atrás de uma abstração. Isso transforma a camada de conveniência num acelerador sobre um conhecimento que continua sendo ensinado, em vez de um substituto que o esconde.
