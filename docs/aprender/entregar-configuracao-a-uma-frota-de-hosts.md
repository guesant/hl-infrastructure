# Entregar configuração a uma frota de hosts

[Ansible](ansible.md) já descreve a distinção central entre um modelo push, onde a máquina do operador inicia a conexão e empurra a configuração para o destino, e um modelo pull, onde o próprio destino puxaria periodicamente sua configuração de um servidor central. Essa escolha de direção, e as variações que cada modelo admite, moldam boa parte de como uma credencial de acesso precisa ser distribuída e protegida ao longo de uma frota de máquinas, um problema que cresce em importância proporcionalmente ao número de hosts envolvidos.

## Push a partir de uma estação administrativa

No modelo push, uma única estação inicia a conexão com cada host e aplica a configuração; a credencial necessária para essa aplicação (uma senha de cofre de segredos, uma chave privada SSH) mora só naquela estação, nunca precisando ser distribuída para os hosts de destino. Isso concentra a superfície de ataque relacionada a essa credencial num único lugar, o que facilita protegê-la, mas também concentra o risco: comprometer essa única estação expõe a capacidade de configurar toda a frota de uma vez. Esse modelo também impõe, por natureza, uma certa disciplina sequencial: aplicar a mesma mudança a muitos hosts significa, na prática, uma execução de cada vez ou em lotes controlados a partir daquela mesma estação, o que limita a velocidade de propagação de uma mudança em uma frota muito grande.

## `ansible-pull` como mecanismo só de auditoria

O `ansible-pull` inverte a direção, fazendo o próprio host clonar um repositório e rodar o playbook contra si mesmo, tipicamente disparado por um agendamento local (um timer do systemd, por exemplo, o mecanismo já descrito em [systemd: units, timers e dependências](systemd-units-timers-e-dependencias.md)). Usado só em modo de verificação, sem aplicar mudança real (o equivalente ao `--check` já descrito em [Ansible](ansible.md)), esse mecanismo funciona como uma auditoria contínua de deriva de configuração, de baixo risco porque só lê o estado atual e o compara ao esperado, sem escrever nada; nesse uso específico, o host nem precisa de uma credencial sensível para rodar a verificação, só acesso de leitura ao repositório que descreve o estado esperado. Rodar esse tipo de verificação em paralelo, com um pequeno atraso aleatório entre a execução em hosts diferentes, evita que uma frota inteira dispare a mesma verificação exatamente no mesmo instante, sobrecarregando o repositório de origem ou qualquer recurso compartilhado que a verificação consulte, e um mecanismo de trava local evita que duas execuções da mesma verificação se sobreponham no mesmo host caso uma disparada anteriormente ainda não tenha terminado.

## `ansible-pull` aplicando configuração de verdade

Usar o mesmo mecanismo para efetivamente aplicar mudanças, não só auditar, muda o cálculo de risco de forma significativa: agora cada host precisa ter, localmente, uma credencial capaz de decifrar o material sensível que o playbook usa, o que significa distribuir essa credencial (ou uma por host, ou uma compartilhada) para toda a frota. Uma credencial compartilhada entre muitos hosts tem uma consequência direta: comprometer qualquer host individual da frota expõe a mesma credencial usada por todos os demais, ampliando o raio de dano de uma única máquina comprometida para o alcance de toda a credencial compartilhada, exatamente o oposto da concentração de risco (mas também de proteção) que o modelo push mantém numa única estação.

## Uma credencial por host, entregue por chave de acesso individual

Um meio-termo entre os dois modelos anteriores usa uma chave de acesso individual por host (uma deploy key, no sentido já descrito em [SSH](ssh.md#chave-pessoal-versus-deploy-key)) para permitir que cada host puxe só o material específico que lhe cabe, de um repositório ou cofre de segredos separado do repositório de configuração em si. Isso combina o modelo pull de configuração (cada host busca sua própria configuração) com uma distribuição própria e isolada de credencial por host, de forma que comprometer um host expõe só a credencial daquele host específico, não uma credencial compartilhada por toda a frota; o custo é operar e rotacionar N credenciais individuais em vez de uma só, um trabalho que cresce proporcionalmente ao tamanho da frota.

Manter esse repositório de material sensível fisicamente separado do repositório que declara a configuração (em vez de tudo no mesmo lugar, com o material sensível cifrado dentro dele) é uma camada de isolamento adicional que vale considerar por si só, independente do modelo de entrega escolhido. Separar os dois limita quem precisa de acesso a cada um de forma mais granular: uma automação ou uma pessoa que só precisa ler a configuração declarada não precisa de acesso nenhum ao repositório de segredos, mesmo cifrados, o que reduz o número de lugares onde uma cópia local desse material sensível pode acabar existindo sem necessidade. O ganho real dessa separação depende de quanto os dois repositórios já eram, de qualquer forma, igualmente privados e igualmente restritos em quem tem acesso: se o repositório de configuração já é privado e já tem o mesmo controle de acesso que o repositório de segredos teria, a camada extra de um segundo repositório rende menos do que renderia num cenário onde o repositório de configuração é mais amplamente acessível (por exemplo, compartilhado com uma equipe maior que não precisa ver segredo nenhum).

## GitOps aplicado à camada de sistema operacional

O mesmo padrão de reconciliação contínua a partir de um repositório git, já descrito para containers e cluster em [ArgoCD e GitOps](argocd.md) e para Podman em [GitOps para Podman: orches e materia](gitops-para-podman-orches-e-materia.md), também pode em princípio ser estendido à camada de sistema operacional de um host, com um agente reconciliando pacotes instalados, configuração de serviço e regras de firewall a partir de um estado declarado em git, de forma parecida a como um controlador reconcilia recursos dentro de um cluster Kubernetes. Esse espaço, fora do mundo especificamente de containers, é menos maduro e mais fragmentado que o GitOps para Kubernetes, com menos ferramentas amplamente adotadas resolvendo esse problema especificamente na camada de sistema operacional; avaliar a maturidade real de uma ferramenta específica antes de depender dela para essa camada continua sendo um passo necessário, dado o estado ainda menos consolidado desse espaço comparado ao GitOps para cargas de trabalho em container.

## Imagem de sistema operacional imutável

Uma abordagem estruturalmente diferente elimina a própria necessidade de aplicar configuração em tempo de execução: uma distribuição de sistema operacional imutável (como as desenhadas especificamente para rodar Kubernetes, distribuindo o sistema como uma imagem completa que se substitui inteira a cada atualização, em vez de pacotes individuais instalados incrementalmente) não sofre deriva de configuração pela própria natureza do modelo, porque não há um estado mutável de pacotes acumulando divergência ao longo do tempo entre o que foi declarado e o que de fato está instalado. O custo dessa abordagem é a migração: adotar um sistema operacional imutável para um ambiente já em produção sob um modelo tradicional de pacotes é uma mudança de arquitetura de fundo, não um ajuste incremental, e nem todo componente de um ambiente heterogêneo (um firewall de borda com uma distribuição própria, um gateway de borda com requisitos específicos) necessariamente tem um caminho maduro de migração para esse modelo.
