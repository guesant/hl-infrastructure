# CodeQL e zizmor

Análise estática de segurança, descrita como SAST em [Scanning de vulnerabilidade](vulnerability-scanning.md), cobre uma família ampla de técnicas, da mais simples (um padrão de texto conhecido como perigoso) até uma análise semântica de verdade, que entende o fluxo de dados dentro do código, não só sua aparência textual. CodeQL e zizmor ocupam esse extremo mais sofisticado, cada um aplicado a um alvo diferente: código de aplicação e a própria definição de um workflow de CI.

## CodeQL: consultar código como se fosse um banco de dados

Um scanner baseado em padrão de texto encontra o que já foi descrito explicitamente como perigoso; ele não deduz uma vulnerabilidade nova a partir de como os dados fluem dentro do programa. CodeQL, mantido pelo GitHub, resolve isso convertendo o código-fonte inteiro num banco de dados relacional que representa sua estrutura semântica completa (não só o texto, mas como uma variável se propaga de uma função para outra, quais caminhos de execução alcançam qual linha), e permite escrever consultas contra esse banco de dados numa linguagem de consulta própria, parecida com SQL na forma de raciocinar. Uma consulta de segurança nesse modelo pode expressar algo como "existe um caminho de dados de uma entrada controlada pelo usuário até uma função de execução de comando, sem passar por nenhuma validação no meio", uma pergunta sobre fluxo de dados que um scanner de padrão de texto simplesmente não consegue formular, porque exige entender como os dados se movem através de várias funções e arquivos diferentes, não como o código se parece isoladamente numa única linha. O GitHub mantém um catálogo de consultas de segurança prontas para as linguagens mais comuns, o que permite adotar essa análise sem escrever consulta própria, reservando consultas customizadas para um padrão de vulnerabilidade específico do próprio projeto.

## zizmor: a definição do workflow de CI como superfície de ataque

Um workflow de GitHub Actions, por ser só um arquivo YAML, tende a receber menos escrutínio de segurança do que o código de aplicação que ele executa, apesar de ter acesso a segredos reais (tokens de deploy, credenciais de nuvem) e de rodar com um nível de confiança implícito alto. Isso criou uma categoria específica de vulnerabilidade: um workflow que interpola, sem sanitização, um valor controlável por quem abre um pull request (o título do PR, o corpo de um comentário) diretamente dentro de um passo `run:` de shell, permite que esse texto seja interpretado como comando em vez de como dado, uma forma de injeção de comando específica de CI; ou um workflow que concede um escopo de token mais amplo do que qualquer passo dele realmente usa, ampliando o estrago possível caso algum passo seja comprometido. zizmor varre a definição de workflows de GitHub Actions procurando exatamente esses padrões: interpolação não sanitizada de valor controlável por quem abre um PR, permissão de token mais ampla que o necessário, uso de uma Action de terceiro referenciada por uma tag mutável em vez de um hash de commit fixo (o mesmo problema de tag flutuante já descrito em [Imagens, registries e Compose](imagens-registries-e-compose.md), aqui aplicado a uma Action em vez de uma imagem de container). O alvo de zizmor não é o código que o CI executa, é a própria definição de como o CI é executado, uma camada de superfície de ataque que só passou a receber uma ferramenta dedicada depois de incidentes reais de comprometimento de pipeline se tornarem comuns o suficiente para justificar essa categoria.
