# VPNs, túneis e bordas de rede

Uma VPN e uma rede overlay resolvem o mesmo problema de fundo, dar a um dispositivo acesso a uma rede que ele não alcançaria normalmente, com tráfego cifrado no caminho, mas com arquiteturas diferentes. Uma VPN clássica cria um túnel até um ponto central (hub-and-spoke): o cliente enxerga a rede atrás desse ponto como se estivesse fisicamente nela, e se o servidor cai, toda comunicação entre clientes para. Uma rede overlay gerenciada cria uma rede virtual própria (mesh), na qual todo membro tem endereço estável e pode falar diretamente com qualquer outro quando possível, sem depender de um ponto central de trânsito para o tráfego de dados, só para a etapa de descoberta e troca de chaves.

OpenVPN usa um protocolo próprio sobre TLS/SSL, modelo cliente-servidor, sobre interface TUN (camada 3) ou TAP (camada 2). WireGuard resolve o mesmo problema com superfície muito menor: cada par tem chaves pública/privada estáticas, conectar dois peers é trocar chaves públicas como se troca uma chave SSH, sem negociação de certificado; vive no kernel Linux desde a 5.6, com código pequeno e auditável. WireGuard puro exige que cada peer conheça o endereço do outro com antecedência e normalmente depende de pelo menos um peer ter porta UDP acessível, sem NAT traversal automático, adequado para topologia simples e estável. Tailscale usa WireGuard como transporte, acrescentando um plano de controle central que troca chaves automaticamente, autentica via SSO e resolve NAT traversal sem configuração manual; Headscale é a implementação open source autohospedada do mesmo servidor de coordenação. ZeroTier resolve o mesmo problema com protocolo próprio, não WireGuard, criando uma rede virtual de camada 2 com controlador e agentes, descoberta via STUN/UDP hole punching. A escolha entre Tailscale e ZeroTier se resume a identidade (SSO facilita revogar acesso) versus necessidade de comportamento de camada 2 (broadcast, multicast). Uma VPN/overlay é o que torna praticável restringir a API do Kubernetes (porta 6443) por origem em vez de publicá-la: a regra de firewall libera a porta só para o intervalo de endereços da VPN, e qualquer máquina administrativa entra primeiro nessa rede privada.

## Túneis de exposição: o problema oposto

VPN move o operador para dentro de uma rede; um túnel de exposição move um serviço para fora dela, publicando algo que já está numa rede privada para qualquer cliente da internet, sem que esse cliente precise de VPN nenhuma. O `cloudflared`, conector do Cloudflare Tunnel, inicia uma conexão de saída da origem até a borda da Cloudflare, atravessando o firewall local como qualquer conexão de saída comum; não existe porta de entrada para abrir. Um registro DNS aponta o nome público para esse túnel, e a Cloudflare roteia requisições de volta pela mesma conexão. O ponto que exige atenção: o TLS público termina na borda da Cloudflare, não na origem, então a Cloudflare tem acesso ao conteúdo decifrado em algum ponto do caminho, o preço de terceirizar a borda para não expor porta nenhuma. ngrok resolve o mesmo problema com um modelo historicamente mais associado a desenvolvimento: `ngrok http <porta>` cria uma URL pública imediata, efêmera no uso gratuito; planos pagos oferecem domínios reservados e uso como ingress de produção. Ambos compartilham o mesmo risco: dependência de um terceiro estar no ar, TLS terminado numa borda alheia, e um nome público apontando para infraestrutura que não é do operador.

DNS dinâmico (DDNS) resolve um problema diferente: existe conectividade direta possível, mas o IP público muda sem aviso, o caso de uma conexão residencial comum. Um cliente consulta periodicamente o próprio endereço público e, quando muda, atualiza o registro `A`/`AAAA` via API do provedor, formalizado pela operação `UPDATE` do DNS (RFC 2136). DDNS e túnel de exposição não competem: DDNS resolve "meu IP muda, mas quero ser alcançado diretamente nele"; túnel resolve "não quero (ou não posso) ser alcançado diretamente". Um roteador atrás de CGNAT, sem porta de entrada abrível, elimina DDNS como opção sozinha e deixa o túnel como o caminho que resta.

## Plataformas dedicadas de borda

Um roteador doméstico resolve segmentação de forma limitada: NAT, uma rede local, talvez uma exceção manual de porta. Quando o objetivo passa a ser segmentar redes de verdade ou aplicar política antes de qualquer host, a resposta comum é um sistema operacional dedicado de rede. RouterOS, da MikroTik, roda em hardware próprio ou em x86 comum, construído sobre kernel Linux mas expondo interface própria (Winbox, web, CLI hierárquica); o que o diferencia de um roteador doméstico não é uma feature exclusiva, é profundidade: OSPF e BGP, firewall com granularidade equivalente ao netfilter, VLANs 802.1Q completas, modelagem de tráfego com HTB, VPN nativa. pfSense, construído sobre FreeBSD, cobre firewall stateful, VPN, NAT, VLANs, failover de múltiplos links de WAN, tudo por interface web; o OPNsense nasceu como fork em 2015 por divergências de governança, e uma decisão da OMPI em 2017 separou juridicamente as marcas dos dois projetos, que hoje convergiram para a mesma categoria. Um equipamento dedicado faz sentido a partir do momento em que existe mais de uma rede lógica para separar (gerência, cluster, convidados) ou mais de um link de internet; o firewall do host continua necessário mesmo com uma borda bem configurada, como última linha de defesa contra um host já comprometido dentro da mesma rede segmentada.
