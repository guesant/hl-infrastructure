# GitOps para Podman: orches e materia

O padrão GitOps descrito em [ArgoCD e GitOps](argocd.md), um controlador dentro do ambiente observando um repositório git e reconciliando continuamente o estado real até bater com o que o repositório declara, não depende de Kubernetes existir; depende só de haver algum mecanismo de reconciliação e algum jeito declarativo de descrever o estado desejado. orches e materia aplicam exatamente esse padrão a um único host rodando Podman e systemd, sem cluster nenhum por trás, usando [Podman Quadlets](podman-quadlets.md) como o formato declarativo que substitui o manifesto Kubernetes de uma Application do Argo CD.

## orches: o caso mais simples possível

orches assume a forma mais enxuta desse padrão: um repositório git contém arquivos Quadlet (e outras units systemd genéricas, não só containers) na raiz, e o binário do orches, rodando ele mesmo dentro de um container gerenciado pelo systemd, verifica esse repositório periodicamente (a cada dois minutos por padrão) e aplica qualquer mudança encontrada, copiando os arquivos para o diretório de Quadlets do sistema e recarregando a configuração do systemd. Não há conceito de múltiplas aplicações isoladas nem templating de valores por ambiente; o repositório inteiro é a unidade de sincronização, análogo a uma única Application do Argo CD sem o padrão app-of-apps por trás. Essa simplicidade é a proposta de valor declarada do projeto: `orches init` aponta para um repositório e o restante da operação se resume a `orches sync` (forçar uma verificação imediata) ou `orches switch` (trocar de repositório de origem), sem exigir entender mais conceitos que esses.

## materia: lifecycle completo por componente

materia resolve o mesmo problema geral com um modelo mais rico, organizado em torno do conceito de **componente**: um pacote nomeado de Quadlets e arquivos de dados associados, tratado como uma unidade de instalação, atualização e remoção independente das demais. Isso resolve uma limitação real do modelo mais simples do orches, onde remover um serviço do repositório e aplicar a mudança depende do operador lembrar de também remover manualmente qualquer arquivo de dado ou configuração que aquele serviço tivesse deixado para trás; materia rastreia explicitamente quais recursos pertencem a qual componente, e quando um componente deixa de estar atribuído a um host, para os serviços associados e remove os recursos que ele havia criado, em vez de deixar artefatos órfãos acumulando silenciosamente. materia também resolve, nativamente, um problema que o padrão GitOps sempre enfrenta quando o estado desejado inclui algo sensível: arquivos de componente podem ser templados com variáveis e segredos, com decifragem via age (o mesmo mecanismo assimétrico descrito em [Criptografia de segredos no Git](criptografia-de-segredos-no-git.md)) acontecendo no momento da instalação, em vez de exigir que o segredo já exista em texto claro no host antes do componente ser aplicado.

## O ponto em comum: reconciliação pull, nunca push

Tanto orches quanto materia preservam a característica mais importante do GitOps de verdade, já discutida a propósito do Argo CD: a sincronização é sempre puxada de dentro do ambiente que está sendo gerenciado, por um agente rodando localmente que consulta o repositório, nunca empurrada de fora por um pipeline de CI que se conecta ao host e aplica uma mudança. Isso preserva a mesma vantagem de segurança do modelo original, o ambiente gerenciado nunca precisa expor uma credencial de escrita para um sistema de CI externo, só uma credencial de leitura para o próprio repositório git, e o mesmo tipo de garantia de auditabilidade: todo estado do host, em teoria, corresponde a um commit específico revisável no repositório, não a uma sequência de comandos manuais que ninguém mais consegue reconstruir depois.

## Quando um host único com Podman faz mais sentido que um cluster

A existência dessas ferramentas é, em si, um dado sobre quando vale a pena adotar Kubernetes e quando não vale: [Orquestradores de containers: Compose, Swarm e Kubernetes](orquestradores-de-containers.md) já cobre os critérios gerais dessa escolha, mas o caso específico de "um host único, sem necessidade real de agendamento entre múltiplas máquinas, mas ainda assim querendo o modelo de operação GitOps" é exatamente o nicho que orches e materia preenchem, oferecendo declaratividade e reconciliação contínua sem pagar o custo operacional de rodar um control plane Kubernetes inteiro (mesmo um K3s de nó único) só para obter esse benefício.
