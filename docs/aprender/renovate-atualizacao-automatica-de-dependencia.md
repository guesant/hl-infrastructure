# Renovate: atualização automática de dependência

Manter uma dependência de terceiros atualizada manualmente exige que alguém, periodicamente, revise cada manifesto de dependência do projeto, compare a versão declarada com a mais recente disponível, e abra a mudança. Esse trabalho tedioso e repetitivo tende a ser adiado indefinidamente na prática, e um projeto sem esse hábito acumula dependências cada vez mais distantes da versão atual, o que torna uma eventual atualização em lote muito mais arriscada do que várias atualizações pequenas e frequentes: quanto maior o salto de versão, maior a chance de uma mudança de comportamento incompatível se esconder no meio do caminho. Renovate resolve isso automatizando o ciclo inteiro de descoberta e proposta de atualização, deixando só a decisão de aceitar com uma pessoa.

## Managers: onde uma versão pode estar escrita

O primeiro problema que Renovate precisa resolver antes de sugerir qualquer atualização é descobrir onde, dentro do repositório, uma versão de dependência está declarada, e esse "onde" muda de formato conforme o ecossistema: um `package.json` para pacotes npm, um `Chart.yaml` para dependências de um chart Helm, a linha `FROM` de um `Dockerfile`, o campo `uses:` de um workflow do GitHub Actions. Cada um desses formatos tem um **manager** embutido no Renovate que sabe reconhecer e propor atualização para aquele formato específico, sem configuração adicional. O caso mais interessante, e que revela os limites desse reconhecimento automático, é quando uma versão está embutida num lugar que nenhum manager embutido reconhece: uma variável dentro de um arquivo YAML de propósito próprio, ou um comentário estruturado dentro de um `justfile`. Para isso existe o **manager customizado por expressão regular**, onde quem configura o Renovate declara explicitamente um padrão de texto que captura a versão atual, o nome lógico da dependência e a fonte de dados (`github-releases`, `docker`, um repositório Helm específico) a consultar para saber se existe uma versão mais nova. Isso estende a cobertura de "atualização automática" para qualquer lugar onde uma versão apareça em texto, não só os formatos que já têm um manager pronto, ao custo de escrever e manter essa expressão regular corretamente.

## Versionamento: nem toda dependência segue semver

Comparar "a versão atual" com "a versão mais nova disponível" pressupõe uma forma de ordenar versões, e diferentes ecossistemas seguem esquemas diferentes: versionamento semântico (`major.minor.patch`, onde só um aumento de `major` sinaliza uma mudança incompatível) é o mais comum, mas está longe de ser universal. Uma imagem de container com uma tag como `2026.07` segue um esquema de versionamento por calendário, onde a ordem cronológica de publicação é o que importa, não uma hierarquia de compatibilidade sinalizada pelo próprio número. Renovate precisa saber qual esquema de versionamento uma dependência específica segue para propor "a próxima versão razoável" corretamente; tratar uma versão de calendário como se fosse semver produz comparações sem sentido, e o inverso também.

## `minimumReleaseAge`: atraso deliberado como mitigação de supply chain

Adotar a versão mais nova de uma dependência no instante em que ela é publicada parece a escolha mais atualizada possível, mas carrega um risco de supply chain específico: uma dependência comprometida (uma conta de mantenedor sequestrada publicando uma versão maliciosa, por exemplo) costuma ser descoberta e revogada em dias, não em minutos, e quem atualiza imediatamente após a publicação está exposto exatamente nessa janela de detecção. Configurar uma idade mínima de lançamento antes de considerar uma versão elegível para atualização automática (esperar sete dias, por exemplo, antes de propor a atualização) é uma mitigação direta a esse risco: dá tempo para a comunidade descobrir e reportar um problema antes que a automação do próprio projeto adote a versão comprometida. O custo é óbvio, um atraso deliberado na adoção de correções legítimas também, incluindo correções de segurança legítimas que se beneficiariam de adoção rápida; a resposta comum a essa tensão é isentar dessa espera as atualizações que o próprio scanner de vulnerabilidade do sistema já sinalizou como correção de uma falha conhecida, tratando esse caso como uma exceção deliberada à regra geral de esperar.

## Agrupamento, automerge e o que fica para revisão humana

Sem agrupamento, um projeto com muitas dependências geraria uma avalanche de pull requests individuais, um para cada atualização disponível, ruído suficiente para que ninguém revise nenhum com atenção real. Agrupar dependências relacionadas (todas as bibliotecas do mesmo ecossistema, por exemplo, ou a imagem de uma ferramenta e o binário equivalente que um script baixa separadamente, quando os dois precisam avançar sempre juntos) numa única proposta reduz esse ruído, ao custo de uma falha em qualquer membro do grupo bloquear a aceitação de todo o grupo. Uma política de automerge para atualizações de baixo risco (tipicamente uma atualização de patch, ou uma atualização cujo pipeline de verificação automatizado já cobre o comportamento relevante) remove até a etapa de aprovação manual para esse subconjunto específico, reservando a atenção humana para o que realmente precisa dela: uma mudança de versão maior, mais propensa a alterar comportamento de um jeito que só um humano com contexto do projeto consegue avaliar direito.

## Manter o digest em dia, não só a tag

Quando uma dependência é referenciada por tag e digest juntos, a prática de pinagem detalhada em [Pinagem por digest e hash em cada ecossistema](pinagem-por-digest-e-hash.md), Renovate cumpre um segundo papel além de propor uma tag nova: mesmo quando a tag declarada não muda (uma imagem de sistema operacional atualizada semanalmente sob a mesma tag `slim`, por exemplo), o conteúdo por trás dela muda, e o digest fixado no manifesto fica, sem essa atualização, apontando para uma versão cada vez mais antiga da mesma tag. Uma regra de Renovate dedicada a isso mantém o digest de uma referência tag-mais-digest em sincronia com a tag declarada, mesmo sem nenhuma mudança de versão visível no texto do manifesto, o que evita a armadilha de uma imagem "pinada" na aparência do manifesto continuar envelhecendo silenciosamente por baixo.

## Checksums derivados da versão

Alguns artefatos deste repositório não são referenciados como imagem com tag e digest. O instalador do K3s e os charts do Cilium e do Argo CD possuem uma versão em `ansible/group_vars/all/versions.yml` e um checksum do artefato correspondente no mesmo arquivo. O script `.tools/update-version-checksums.sh` baixa os artefatos selecionados por essas versões, calcula os checksums e compara ou atualiza os campos relacionados.

`just version-checksums` executa a verificação sem modificar arquivos. `just version-checksums-update` recalcula e grava os valores. O Renovate executa a atualização no branch da própria proposta sempre que altera `versions.yml`, de modo que a nova versão e seu checksum entrem no mesmo pull request. O CI executa apenas a verificação e falha se os campos divergirem.
