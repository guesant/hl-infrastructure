# Alertas acionáveis e distributed tracing

Um alerta que dispara sem que ninguém possa agir sobre ele é pior do que nenhum alerta, treina a equipe a ignorar notificações, o que esconde os alertas reais quando eles aparecem. Um alerta acionável liga uma condição mensurável a uma resposta esperada: a severidade deveria ser definida pela resposta esperada, não pelo nome técnico do componente, `critical` significa acionar alguém agora com ação possível, `warning` significa revisar antes que vire impacto, `info` não deveria acordar ninguém. Um `for` (duração mínima antes de disparar) evita ruído de flutuações normais, mas precisa ser compatível com o tempo real tolerável, um `for` longo demais atrasa a detecção de um incidente real. *Recording rules* pré-computam expressões caras, reduzindo a carga de avaliação repetida, mas não substituem uma regra de alerta, são uma otimização, não uma estratégia em si. Um alerta é acionável quando existe resposta clara e possível, um runbook acessível durante a indisponibilidade, e a condição está ligada a impacto real, não a um valor técnico interessante; para condições puramente informativas sem ação esperada, o lugar é um dashboard, não um alerta, porque um alerta sem critério de ação é ruído.

## O que um trace mostra que métricas isoladas não mostram

Uma métrica de latência por serviço responde "o serviço B está lento", mas não responde por quê quando B depende de uma consulta ao banco e de uma chamada ao serviço C; sem um identificador comum, investigar significa correlacionar logs de serviços diferentes manualmente. Um trace atribui um identificador único a cada requisição (`trace_id`) e registra cada etapa como um span, com início, duração e referência ao span pai; o conjunto de spans de um mesmo `trace_id` reconstrói o caminho completo através de todos os serviços atravessados, com a duração exata de cada etapa. OpenTelemetry não é um sistema de armazenamento ou visualização, é uma especificação aberta com SDKs para várias linguagens que padroniza como uma aplicação gera spans, métricas e logs e como esses dados são exportados; a aplicação é instrumentada uma única vez contra o SDK, e o destino (Jaeger, ou qualquer backend compatível com OTLP) é uma decisão de configuração do exportador, não do código, o que permite trocar de backend depois sem reinstrumentar. Jaeger é um sistema completo de tracing, recebendo spans via OTLP, armazenando em um backend configurável (memória para testes, Elasticsearch ou Cassandra para produção) e oferecendo uma interface para explorar traces e comparar latências. Grafana Tempo é uma alternativa que resolve o mesmo problema recebendo spans pelo mesmo protocolo OTLP, mas se integra diretamente a um Grafana já usado para métricas e logs, unificando os três sinais no mesmo painel em vez de exigir uma interface própria como a do Jaeger; a escolha entre os dois depende mais de onde a equipe já centraliza a observação do que de uma diferença técnica decisiva entre eles. Registrar 100% das requisições como traces completos tem custo de armazenamento proporcional ao volume total; amostragem descarta uma fração antes de exportar, mantendo uma amostra estatisticamente representativa, tipicamente entre 1% e 10% em produção de alto volume, 100% em ambientes de desenvolvimento com tráfego baixo. Tracing se justifica quando a aplicação já é distribuída entre múltiplos serviços que se chamam em cadeia e métricas agregadas não bastam para localizar a origem de uma latência; não é prioridade inicial de observabilidade de um cluster pequeno ou de uma aplicação monolítica, onde métricas e logs já respondem à maioria das perguntas operacionais.
