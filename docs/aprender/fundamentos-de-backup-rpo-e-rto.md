# Fundamentos de backup, RPO e RTO

Um backup é, por definição, uma cópia isolada no tempo e no espaço da escrita corrente: só essa cópia permite voltar a um estado anterior a um erro, físico (disco perdido) ou lógico (exclusão acidental, corrupção, ataque). Três mecanismos são frequentemente confundidos: uma **réplica** é uma cópia síncrona em tempo real, protegendo contra perda física mas propagando qualquer escrita destrutiva com a mesma velocidade de uma legítima; um **snapshot** é um ponto de retorno rápido do estado de um volume num instante específico, normalmente permanecendo no mesmo domínio de falha do original; um **backup** é uma cópia isolada, tipicamente num destino externo, com retenção e controles de acesso próprios. Cada camada protege contra um tipo diferente de falha, nenhuma substitui as demais; réplica sozinha nunca protege contra erro lógico, snapshot sozinho não protege contra a perda do storage inteiro, backup é o único que cobre os dois cenários combinados, e é obrigatório sempre que o dado não pode ser recriado a partir de outra fonte, bancos de dados, estado de configuração não versionado, credenciais.

Um erro comum é tratar o snapshot do etcd como "o backup do cluster inteiro": ele protege só o estado declarado da API Kubernetes, objetos, ConfigMaps, Secrets, metadados, não o conteúdo de um `PersistentVolume`, dados de um banco de dados que vivem dentro do volume, nem imagens de container. Um cluster completo tem pelo menos quatro categorias de dado que precisam de estratégias próprias: estado da API (etcd), dados de volumes, dados de bancos de dados, e material de bootstrap que vive fora do cluster por design, como chaves de criptografia e credenciais de secret store. O snapshot do etcd sozinho só é suficiente para um cluster sem PVCs nem bancos de dados, um cenário raro além de laboratórios muito simples; assim que qualquer workload usa armazenamento persistente, cada categoria de dado precisa da própria linha numa matriz de proteção, com RPO, RTO, frequência e teste de restauração próprios.

## RPO e RTO: as duas perguntas que toda estratégia precisa responder

**RPO** (Recovery Point Objective) é a perda máxima de dados tolerável, medida em tempo; um RPO de 15 minutos significa que, no pior caso, a restauração pode perder até 15 minutos de dados desde o último ponto recuperável, não que o backup "roda a cada 15 minutos" necessariamente, mas que o mecanismo garante um ponto recuperável dentro dessa janela. **RTO** (Recovery Time Objective) é o tempo máximo tolerável para restabelecer o serviço, contado do início do incidente até a funcionalidade restaurada, não apenas até os arquivos terem sido copiados de volta. Nenhum dos dois é uma meta abstrata; ambos só têm valor quando medidos contra um teste de restauração real, uma retenção diária não prova um RPO de 15 minutos, um script de restore nunca executado não prova nenhum RTO. RPO define a frequência mínima de backup e a existência de logs incrementais; RTO define o procedimento de restauração aceitável, um restore manual demorado pode não caber num RTO curto. Dados de produção com impacto real (financeiro, operacional, de confiança) pedem RPO/RTO rigorosos; ambientes de desenvolvimento ou dados de cache reconstruíveis toleram metas frouxas, uma escolha deliberada e razoável, não um descuido.
