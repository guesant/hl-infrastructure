# CNI

O K3s instala Flannel como CNI padrão porque ele é suficiente para o caso comum, conectividade entre Pods sem configuração adicional; Flannel não implementa `NetworkPolicy`, então um cluster que precisa restringir tráfego entre namespaces precisa substituí-lo por um CNI que suporte políticas de rede. Cilium e Calico são as duas opções mais usadas, e a escolha depende menos de qual é "melhor" e mais de qual modelo técnico se encaixa no kernel disponível e no tipo de política necessária.

Calico, o mais antigo dos dois, gera na configuração padrão regras iptables (ou nftables, dependendo da versão) para aplicar suas políticas, um caminho bem entendido que funciona em kernels antigos e permite roteamento via BGP nativo, útil em topologias que já usam BGP para anunciar rotas entre hosts. Seu suporte a `NetworkPolicy` cobre as camadas 3 e 4, endereço IP, porta, protocolo. Cilium usa eBPF, um mecanismo que executa programas restritos e verificados diretamente dentro do kernel, sem depender de módulos externos nem das chains tradicionais do netfilter; isso exige um kernel recente (5.8 ou superior para os recursos que o Cilium usa), mas permite políticas de camada 7, restringir uma conexão a métodos HTTP específicos ou a consultas DNS para domínios determinados, algo que Calico não faz nativamente. O Cilium também inclui o Hubble, observabilidade de rede que reaproveita os mesmos pontos de instrumentação eBPF para mostrar fluxos entre Pods sem exigir sidecars.

Calico é a escolha mais direta quando o cluster roda num kernel anterior ao exigido pelo Cilium, quando a topologia já depende de BGP entre nós, ou quando as políticas necessárias não passam de filtragem por IP, porta e protocolo. Cilium se justifica quando o cluster precisa de políticas em camada de aplicação, quando observabilidade de tráfego entre serviços é um requisito operacional, ou quando os hosts já atendem ao requisito de kernel sem esforço adicional. Instalar qualquer CNI alternativo num cluster K3s exige desabilitar o Flannel embutido na inicialização do servidor (`--flannel-backend=none`) antes de instalar o CNI escolhido; substituir depois que o cluster já roda com Flannel normalmente exige recriar os nós, porque as regras já aplicadas não são removidas de forma limpa ao trocar de plugin. O recurso `NetworkPolicy` padrão do Kubernetes funciona da mesma forma na definição independentemente de qual CNI o implementa por baixo; quando as políticas exigem controle além disso, o Cilium expõe `CiliumNetworkPolicy`, estendendo a especificação com regras de camada 7 não disponíveis na API padrão nem em Calico.
