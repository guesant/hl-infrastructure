# Feature flags

Uma feature flag (também chamada de feature toggle) separa duas decisões que normalmente andam juntas: quando uma mudança de código é implantada (deployed) e quando ela fica de fato visível ou ativa para quem usa o sistema (released). Sem esse mecanismo, as duas decisões acontecem no mesmo momento, o instante em que o deploy termina; com uma flag, o código de uma funcionalidade nova pode estar presente em produção, implantado e rodando, sem estar ativo para ninguém, até que alguém explicitamente vire a flag, sem precisar de um novo deploy para isso.

## O que isso resolve

Separar deploy de release resolve um problema real de risco e de controle. Implantar uma mudança sem ativá-la permite confirmar, num ambiente de produção real (não uma réplica de homologação, que nunca reproduz cem por cento das condições reais), que o novo código não introduz um efeito colateral inesperado antes de qualquer usuário real depender dele, porque a flag continua desligada enquanto essa confirmação acontece. Isso também separa a velocidade de entrega de código da velocidade de negócio de lançar uma funcionalidade: um time pode integrar código incompleto ou parcialmente pronto em produção continuamente (a prática de integração contínua já descrita em [CI/CD](ci-cd.md) depende disso para funcionar bem, evitando branches de longa duração divergentes), guardado atrás de uma flag desligada, sem que isso signifique que a funcionalidade está disponível para o público antes de estar pronta e aprovada para lançamento.

## Reverter sem reverter o deploy

Um efeito colateral valioso de uma feature flag é oferecer uma forma de reversão muito mais rápida do que reverter um deploy inteiro: se uma funcionalidade recém-ativada causa um problema, desligar a flag remove o comportamento problemático imediatamente, sem precisar reverter o código, reconstruir uma imagem, e reimplantar, um processo que costuma levar bem mais tempo do que trocar o valor de uma flag. Isso muda o cálculo de risco de ativar uma funcionalidade nova: o custo de reverter, se algo der errado, é muito menor do que numa arquitetura sem esse mecanismo, o que por sua vez permite ativações mais frequentes e mais ousadas do que seriam razoáveis sem essa rede de segurança.

## Ativação segmentada: por usuário, por porcentagem, por atributo

Uma flag não precisa ser um interruptor binário para todo mundo ao mesmo tempo. Ativar uma funcionalidade só para uma fração pequena do tráfego (uma porcentagem configurável de usuários, escolhidos de forma consistente para que o mesmo usuário sempre caia do mesmo lado da flag) reduz o impacto de um problema não detectado durante a validação inicial, o mesmo princípio de exposição controlada e crescente já descrito em [Entrega progressiva: canary, blue-green e Argo Rollouts](entrega-progressiva-canary-blue-green-e-argo-rollouts.md), aqui aplicado no nível da lógica de aplicação em vez de no nível do tráfego de rede entre versões de um serviço. Segmentar por atributo (ativar só para usuários de uma organização específica, ou de uma região geográfica específica) permite tanto uma validação restrita a um grupo controlado quanto um modelo de lançamento por fases deliberado, onde diferentes grupos recebem a funcionalidade em momentos diferentes por decisão de produto, não só por cautela técnica.

## Onde isso se sobrepõe, e onde não se sobrepõe, com deploy progressivo

Feature flags e as estratégias de entrega progressiva (canário, blue-green) resolvem problemas parecidos, mas em camadas diferentes, e vale entender a distinção para não tratá-los como intercambiáveis. Entrega progressiva opera no nível de infraestrutura, controlando qual versão do código atende qual fração do tráfego; uma flag opera no nível de aplicação, controlando qual caminho de código dentro da mesma versão executa para qual usuário. Isso significa que uma flag pode ativar ou desativar uma funcionalidade instantaneamente, sem nenhuma mudança de infraestrutura, algo que uma estratégia de canário sozinha não faz (reverter um canário significa reverter o tráfego para a versão anterior, uma operação de infraestrutura). Por outro lado, uma flag não isola completamente dois comportamentos ao nível de processo: os dois caminhos de código, o antigo e o novo, coexistem na mesma versão implantada, o que significa que um bug introduzido pelo código novo, mesmo atrás de uma flag desligada, ainda pode afetar a versão implantada se o bug estiver numa parte do código que roda independentemente do estado da flag (uma falha de compilação, um efeito colateral de inicialização), algo que uma versão de fato separada, como no canário, isolaria com mais garantia. As duas técnicas se complementam bem: usar entrega progressiva para validar que a versão nova do serviço, como um todo, está estável, e feature flags para controlar quais funcionalidades específicas dentro dessa versão estão de fato visíveis.

## O custo de acumular flags

Uma flag que nunca é removida depois de a funcionalidade ser lançada por completo para todo mundo (ou definitivamente descartada) vira uma ramificação de código permanente que ninguém mais precisa, mas que continua existindo, sendo avaliada a cada execução, e acumulando complexidade cognitiva para quem lê o código depois. Um sistema com muitas flags acumuladas ao longo do tempo, sem uma disciplina de removê-las depois que cumpriram seu propósito, tende a acumular combinações de estado cada vez mais difíceis de raciocinar (o comportamento do sistema passa a depender não de uma flag isolada, mas da combinação de várias ligadas ou desligadas simultaneamente), um custo que cresce de forma não linear com o número de flags vivas ao mesmo tempo, e que só uma disciplina deliberada de limpeza periódica evita.
