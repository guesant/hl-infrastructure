# RBAC do Kubernetes

Controle de acesso baseado em papéis (RBAC) é o mecanismo pelo qual o Kubernetes decide se uma identidade, seja uma pessoa autenticando via um provedor externo, seja um Pod agindo em nome de uma ServiceAccount, pode executar uma ação específica sobre um recurso específico. A pergunta que o RBAC responde tem sempre essa forma tripla: quem está pedindo, o que essa pessoa ou processo quer fazer (ler, criar, apagar, listar), e sobre qual tipo de recurso. Sem RBAC, ou com um RBAC mal configurado, a única linha de defesa de um cluster passa a ser a autenticação, provar quem alguém é, sem nenhum controle sobre o que essa identidade autenticada tem permissão de fazer depois de provar quem é.

O modelo se apoia em dois pares de objetos que espelham um ao outro na diferença entre escopo de namespace e escopo de cluster inteiro. Um `Role` declara um conjunto de permissões (verbos como `get`, `list`, `create`, `delete`, aplicados a tipos de recurso como `pods` ou `secrets`) restrito a um único namespace; um `ClusterRole` declara o mesmo tipo de conjunto de permissões, mas sem essa restrição, podendo abranger recursos de todo o cluster ou recursos que nem pertencem a um namespace, como `nodes`. Nenhum dos dois, por si só, concede nada a ninguém: um `Role` ou `ClusterRole` é apenas uma lista de permissões nomeada, uma definição à espera de ser atribuída a alguém. Essa atribuição é o papel do segundo par: uma `RoleBinding` liga um `Role` (ou até um `ClusterRole`, aplicado então apenas dentro do namespace da binding) a uma identidade específica, concedendo as permissões daquele papel só dentro daquele namespace; uma `ClusterRoleBinding` liga um `ClusterRole` a uma identidade em escopo de cluster inteiro, concedendo as mesmas permissões em qualquer namespace.

Essa separação entre definição (`Role`/`ClusterRole`) e atribuição (`RoleBinding`/`ClusterRoleBinding`) é o que permite reutilizar a mesma definição de permissões para conceder o mesmo nível de acesso a identidades diferentes, ou ao mesmo tempo restringir uma definição ampla a um escopo estreito: um `ClusterRole` genérico de "operador de aplicação" pode ser vinculado por uma `RoleBinding` a um namespace específico, concedendo aquele conjunto de permissões só ali, mesmo que a definição em si não tenha restrição de namespace nenhuma. Um princípio prático decorre diretamente disso: conceder o menor conjunto de permissões que realmente atende à necessidade (o princípio do menor privilégio) é mais fácil de aplicar corretamente vinculando papéis estreitos e específicos a namespaces específicos do que distribuindo `ClusterRoleBinding`s amplas por comodidade, porque cada `ClusterRoleBinding` amplia o raio de dano de qualquer identidade que a receba para o cluster inteiro.

Quando quem age não é uma pessoa, mas um Pod, essa identidade vem de uma ServiceAccount, um objeto Kubernetes que representa a identidade daquele workload perante a própria API. Todo Pod roda sob alguma ServiceAccount, a `default` do namespace quando nenhuma é especificada explicitamente, e as permissões efetivas daquele Pod contra a API são exatamente as que uma `RoleBinding` ou `ClusterRoleBinding` concede àquela ServiceAccount, nada mais. Um controlador que precisa listar Pods de outros namespaces, por exemplo, só consegue fazer isso se sua ServiceAccount tiver uma binding que conceda essa permissão especificamente; sem ela, uma chamada à API retorna um erro de proibição, não um erro de rede ou de conectividade, um sintoma que vale diferenciar ao diagnosticar por que um controlador não está reagindo a mudanças que deveria observar.
