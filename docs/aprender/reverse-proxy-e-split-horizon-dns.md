# Reverse proxy e split-horizon DNS

Um reverse proxy fica na frente de um conjunto de serviços e decide, para cada requisição, qual backend deve atendê-la; a distinção que dá nome à categoria é a posição em relação ao cliente: um forward proxy age em nome do cliente, um reverse proxy age em nome dos servidores, então do ponto de vista de cada backend todo tráfego parece vir do proxy, e do ponto de vista do cliente a resposta parece vir diretamente do serviço solicitado. Três critérios decidem o destino, não mutuamente exclusivos: **roteamento por path**, usando o caminho da URL, com a limitação de que a aplicação por trás precisa saber que está sendo servida a partir de um subcaminho, não da raiz, ou quebra ao gerar links absolutos; **roteamento por host**, usando o cabeçalho `Host` ou, em TLS, o SNI, evitando o problema de subcaminho ao custo de precisar de um domínio por serviço e um certificado que os cubra; e o caso particular do **SNI**, que acontece antes da descriptografia, o cliente TLS enviando o domínio desejado em texto claro no `ClientHello`, permitindo que o proxy decida o backend sem terminar a conexão ele mesmo. Nginx e Apache são proxies de propósito geral configurados por arquivos estáticos; HAProxy prioriza throughput em volumes altos; Traefik se diferencia descobrindo rotas automaticamente a partir de labels do Docker ou recursos do Kubernetes, a escolha mais comum em clusters justamente por essa integração nativa. Um proxy que roteia por host precisa de certificado válido para cada domínio: um wildcard cobre qualquer subdomínio com um único certificado, mas exige validação DNS; SANs múltiplos listam cada domínio explicitamente, mas exigem reemissão a cada domínio novo; a emissão automatizada via cert-manager é a abordagem recomendada dentro do Kubernetes, eliminando gestão manual de renovação.

## Split-horizon DNS

Split-horizon DNS é uma configuração em que o mesmo nome resolve para endereços diferentes dependendo de quem consulta: um cliente na rede interna recebe um endereço, um cliente na internet recebe outro, ou nenhum. Isso resolve o dilema de um cluster que expõe serviços de administração (Grafana, Prometheus, ArgoCD): publicá-los na internet é superfície de ataque desnecessária, mas acessá-los sem DNS nenhum normalmente significa depender de `kubectl port-forward`, um comando manual repetido a cada sessão. Um administrador acessando via VPN ou bastion consulta o mesmo nome, `grafana.internal`, que resolve, nessa visão interna, para um endereço que um reverse proxy interpreta para rotear até o Pod correto; a internet pública nunca vê esse nome, porque a zona que o resolve só existe dentro da rede interna. Quando o resolvedor interno responde `127.0.0.1` para esse nome, o endereço se refere à própria máquina que consulta, porque o reverse proxy roda no mesmo host que resolve o DNS para o administrador, seja um bastion, um gateway de VPN ou o próprio túnel até o ponto de entrada; a resolução aponta para o localhost desse ponto, e o proxy decide o backend real a partir do nome informado na conexão, tipicamente via SNI, permitindo que várias conexões endereçadas a serviços diferentes cheguem todas à mesma porta 443.

Split-horizon DNS se encaixa bem em serviços de administração que só devem ser alcançáveis por quem já tem acesso à rede interna, eliminando `port-forward` manual sem expor nada publicamente; não é a ferramenta certa para serviços que já precisam ser públicos, que resolvem normalmente por DNS público, nem simplifica ambientes com múltiplas redes segmentadas exigindo visões de DNS totalmente distintas, onde a complexidade se equipara à de operar DNS público separado por segmento. Uma configuração completa depende de quatro peças: um servidor DNS interno respondendo só para consultas da rede confiável, um reverse proxy roteando por SNI ou host na mesma porta, certificados válidos para cada domínio interno, e uma rota de acesso à rede interna (túnel SSH, VPN, ou uma máquina já dentro do perímetro).
