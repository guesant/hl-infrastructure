# Sinais de observabilidade e saúde de aplicação

Observabilidade não é uma ferramenta, é a capacidade de responder perguntas sobre o estado interno de um sistema a partir de sinais externos. Três sinais cobrem perguntas diferentes, e nenhum substitui os outros. **Métricas** são amostras numéricas organizadas como séries temporais, contadores, gauges, histogramas; respondem "quanto" e "com que frequência", são baratas de armazenar e ótimas para alertas e agregações, mas não guardam o contexto de uma execução específica. **Logs** são registros discretos de eventos; respondem "o que aconteceu exatamente nesta execução", custam mais para armazenar e consultar em volume, e frequentemente contêm dados sensíveis que exigem tratamento. **Traces** capturam o caminho e a duração de uma operação através de múltiplos serviços, dividida em spans; respondem "onde o tempo foi gasto" numa requisição distribuída. Os três se correlacionam por tempo, cluster, namespace e, quando adotado, um `trace_id` comum, mas um identificador de requisição nunca deve virar label de métrica, porque criaria uma série nova por requisição. Métricas vêm sempre primeiro, o sinal mais barato, cobrindo a maioria dos alertas de disponibilidade e capacidade; logs entram quando métricas não explicam a causa de um erro específico; traces entram quando a aplicação já é distribuída entre múltiplos serviços e a origem de uma latência não é óbvia a partir de métricas isoladas por serviço.

## Do Pod Running à aplicação de fato disponível

`kubectl get pods` mostrando `Running` não prova que uma aplicação está funcional. `Running` significa que o container iniciou e não terminou; `Ready` significa que a `readinessProbe` configurada passou, mas uma probe mal desenhada pode não verificar nada relevante. Mesmo com Pods `Ready`, uma dependência externa degradada (banco lento, fila cheia) pode deixar a aplicação de fato indisponível para o consumidor, sem que nenhum sinal interno do Kubernetes capture isso; a camada final, disponibilidade percebida, só é medida observando a operação do ponto de vista de quem consome o serviço. Sinais internos bastam para detectar falhas de infraestrutura óbvias, onde a causa é clara a partir do estado do Kubernetes; não bastam para confirmar que o serviço realmente atende ao consumidor, especialmente quando dependências externas podem degradar sem que nenhuma probe interna detecte.

Duas probes cumprem papéis diferentes o suficiente para nunca deveriam compartilhar o mesmo endpoint com a mesma semântica: uma `livenessProbe` que falha repetidamente faz o kubelet reiniciar o container, um remédio adequado para quando o processo travou de um jeito do qual só um reinício o tira; uma `readinessProbe` que falha apenas remove o Pod da lista de endpoints prontos de um `Service`, sem reiniciar nada, um remédio adequado para uma condição temporária (uma dependência externa lenta, um cache ainda aquecendo) da qual o processo se recupera sozinho assim que a condição passa. Fazer a liveness verificar uma dependência externa é o erro mais comum dessa dupla: uma falha momentânea de rede até um banco de dados não deveria derrubar o processo que a está reportando, porque reiniciar não resolve um problema que não está dentro do processo, só adiciona uma indisponibilidade nova (o tempo de reinicialização) em cima da original.

**Monitoramento de caixa-branca** (whitebox) usa instrumentação interna, métricas expostas pela própria aplicação, logs, traces, enxergando o interior do sistema; sua limitação é que se o sistema de monitoramento e a aplicação compartilham a mesma infraestrutura, uma falha ampla pode derrubar os dois juntos, deixando o observador cego exatamente quando mais precisa enxergar. **Monitoramento de caixa-preta** (blackbox) observa o sistema de fora, sem conhecimento do interior, um teste de DNS, um handshake TLS, uma requisição HTTP completa simulando um usuário; não explica a causa de uma falha, mas detecta a indisponibilidade mesmo quando a instrumentação interna também está fora do ar. Caixa-branca é onde a investigação de causa realmente acontece, depois que um problema já foi detectado; caixa-preta é necessária sempre, como complemento, porque é o único sinal que sobrevive à perda completa do cluster ou da plataforma de observabilidade interna, e por isso deveria rodar fora do domínio de falha do que observa, nunca dentro do próprio cluster monitorado. O `blackbox-exporter` é a implementação mais comum desse tipo de sondagem dentro do próprio ecossistema Prometheus: transforma o resultado de uma sondagem HTTP, TCP, ICMP ou DNS contra um endpoint que não expõe métrica nenhuma (respondeu, qual código, quanto tempo levou) numa métrica Prometheus comum. Rodá-lo dentro do cluster para sondar um Service interno é útil e legítimo, mas não é a mesma coisa que o monitoramento externo descrito acima: um `blackbox-exporter` que roda dentro do cluster falha junto com ele numa perda total do host, então complementa a cobertura interna de disponibilidade sem substituir uma sondagem de verdade externa a esse domínio de falha.
