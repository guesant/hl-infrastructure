# Interfaces, rotas e camada 2 no Linux

Para o kernel, uma interface de rede é uma estrutura de dados com nome, índice e propriedades, exista ou não hardware físico por trás: `eth0`/`enp3s0` e `wlan0` representam placas reais, `lo` é o loopback, e `veth0`, `br0`, `wg0` são interfaces virtuais criadas por software. Do ponto de vista da pilha, uma interface virtual se comporta como qualquer outra, o que permite a containers, VPNs e redes overlay funcionarem sem hardware dedicado. `ip link show` lista interfaces e seu estado (`UP`/`DOWN`), que combina duas informações: o estado administrativo (o operador pediu para ativar) e o operacional, no campo `LOWER_UP` (existe portadora física ou lógica de fato); uma interface pode estar `UP` sem `LOWER_UP`, o padrão de um cabo desconectado sem ninguém ter desativado a interface. O MTU define o maior payload sem fragmentação, tipicamente 1500 bytes numa Ethernet; quando uma interface encapsula tráfego dentro de outra, como o backend VXLAN do Flannel, o MTU do túnel precisa de folga em relação ao da interface física, ou o resultado é fragmentação silenciosa. `ip link` opera na camada de enlace (estado, MTU, MAC, tipo de interface); `ip address` opera uma camada acima (endereços IP atribuídos), e uma interface pode carregar mais de um endereço simultaneamente, cada um com escopo `global`, `link` ou `host`. `ip`, do pacote `iproute2`, substituiu o `ifconfig` porque este não lida nativamente com tipos de interface virtual modernos (veth, VXLAN, WireGuard) nem expõe a Routing Policy Database.

## Vizinhança e camada 2

Antes de entregar um quadro a outro host na mesma rede local, é preciso traduzir o IP de destino para o MAC correspondente: ARP faz isso em IPv4, NDP em IPv6 (rodando sobre ICMPv6). O resultado fica na tabela de vizinhança (`ip neigh`), com estados que descrevem a confiança do kernel: `REACHABLE`, `STALE` (ainda usada, mas não reconfirmada), `INCOMPLETE` (resolução em andamento) e `FAILED`. O kernel reconfirma essas entradas periodicamente (Neighbor Unreachability Detection), o que explica por que um IP que muda de MAC volta a funcionar sozinho depois de um intervalo. Uma interface **TUN** opera em camada 3, entregando pacotes IP sem cabeçalho de enlace, o modelo comum para VPNs de acesso remoto e WireGuard; uma **TAP** opera em camada 2, entregando quadros Ethernet inteiros, útil quando protocolos dependentes de broadcast precisam funcionar através do túnel, normalmente conectada a uma bridge. Um **veth pair** são dois pontos de uma mesma interface virtual ligados entre si, como as duas pontas de um cabo: uma ponta entra no network namespace do container, a outra fica no host conectada a uma bridge, que mantém sua própria tabela de aprendizado (FDB) para decidir por qual porta encaminhar cada quadro. Essa combinação, veth pair mais bridge, é o que qualquer CNI monta por baixo para dar a cada Pod uma interface própria.

Uma **VLAN** (802.1Q) marca um quadro com uma tag de 12 bits, permitindo que um switch físico carregue múltiplos domínios de broadcast isolados sem cabeamento separado; o limite de 4094 VLANs nunca atravessa um roteador sozinho, os dois lados precisam de adjacência física. **VXLAN** (RFC 7348) resolve isso encapsulando o quadro Ethernet completo dentro de UDP/IP, identificando cada rede virtual por um VNI de 24 bits, mais de 16 milhões de segmentos possíveis, estendendo uma camada 2 por cima de uma rede já roteada. O backend VXLAN do Flannel, padrão do K3s para a rede de Pods, usa esse mecanismo, com um detalhe de compatibilidade: no Linux usa UDP/8472, não a porta IANA 4789, herdada do módulo do kernel anterior à padronização. O Proxmox VE SDN permite declarar zonas `VLAN`, `VXLAN` ou `EVPN` (VXLAN combinado com BGP) no nível do cluster de hipervisores inteiro.

## Roteamento local

A tabela de roteamento é a estrutura que o kernel consulta para decidir por qual interface e gateway enviar um pacote; quando mais de uma rota poderia servir, o kernel escolhe a mais específica, o critério de longest prefix match. A rota `default` (`0.0.0.0/0`) é o caso extremo, o prefixo menos específico, usado só quando nenhuma rota mais longa corresponde. O kernel mantém três tabelas por padrão: `local`, `main` (onde `ip route add` insere por padrão) e `default` (vazia). Policy routing resolve o caso em que a decisão de rota precisa depender de algo além do destino, como o endereço de origem: múltiplas tabelas adicionais mais a RPDB (`ip rule`), que decide qual tabela usar para cada pacote antes de qualquer tabela ser consultada. O exemplo motivador é um host com duas saídas de rede, onde uma tabela extra por interface e uma regra `ip rule add from <origem> table <tabela>` garante que uma conexão que chegou por uma interface também responda por ela, em vez de seguir a rota padrão da `main`.
