# TLS, mTLS e confiança de rede

TLS resolve três problemas para uma conexão que já existe em camada de transporte: confidencialidade, integridade, e autenticação do servidor perante o cliente. TLS 1.3 (RFC 8446) completa o handshake numa única ida e volta na maioria das conexões: o cliente envia um `ClientHello` já com uma proposta de material de chave, o servidor responde com `ServerHello`, certificado e prova de posse da chave privada, e a partir do `ServerHello` toda mensagem já viaja cifrada. O TLS 1.3 removeu os mecanismos de troca de chave sem sigilo direto, então toda cifra suportada hoje garante forward secrecy: comprometer uma chave privada no futuro não permite decifrar tráfego capturado no passado.

Um certificado X.509 associa uma chave pública a uma identidade, atestada pela assinatura de quem o emitiu; o campo Subject Alternative Name (SAN) é o mecanismo correto de verificação de host (RFC 6125), não mais o Common Name legado. É por isso que adicionar um endereço novo à API do K3s exige atualizar a lista `tls-san` do certificado do servidor. A confiança sobe uma cadeia até uma CA raiz já confiável pelo sistema; um certificado autoassinado produz aviso porque a cadeia existe mas termina numa raiz que ninguém reconhece. Certificados públicos, via ACME (o protocolo que o Let's Encrypt popularizou), servem qualquer serviço exposto; uma CA interna serve tráfego que nunca sai da rede do operador. O campo SNI, parte do `ClientHello`, carrega o domínio desejado em texto claro antes de qualquer chave existir, permitindo que um proxy roteie sem terminar TLS. Na **terminação**, o proxy guarda a chave privada e pode rotear por conteúdo de camada 7; no **passthrough**, o proxy nunca decifra, só encaminha os bytes cifrados escolhendo o backend pelo SNI.

TLS comum autentica só o servidor; **mTLS** exige que o cliente também apresente um certificado válido via `CertificateRequest`, então os dois lados provam identidade antes de qualquer dado trafegar. Isso importa quando não existe um humano digitando senha e a identidade precisa ser verificável só pela conexão: o K3s usa esse padrão para o kubelet se autenticar perante a API e para membros do etcd embutido se autenticarem entre si, nenhuma dessas conexões dependendo de senha compartilhada. Um service mesh como Istio ou Linkerd estende a mesma ideia para dentro da malha de Pods, com um sidecar emitindo identidade própria via certificado para cada Pod. Um certificado de vida curta reduz o estrago de uma chave comprometida, mas só é viável com renovação automatizada, o papel do cert-manager; revogação antes do vencimento é um problema mal resolvido pelo ecossistema TLS (CRL e OCSP dependem do cliente consultá-las), e a resposta prática da maioria das infraestruturas modernas é reduzir a validade a ponto de a revogação se tornar menos necessária.

## BGP, AS e confiança de rota

BGP resolve um problema diferente do TLS: trocar rotas entre redes de organizações diferentes que não confiam automaticamente umas nas outras, o protocolo que forma o roteamento da internet pública entre provedores. Um Sistema Autônomo (AS, RFC 1930) é um grupo de prefixos IP operado sob uma única política de roteamento; o ASN identifica esse AS de forma única. O Flannel, CNI embutido no K3s, pode operar em modo BGP em vez do VXLAN mais comum, e o MetalLB usa BGP para anunciar IPs de `Service LoadBalancer` a um roteador de borda. Redes que usam BGP internamente, sem participar do roteamento global, usam ASNs privados (RFC 6996, `64512`-`65534`), o mesmo princípio dos blocos IP privados da RFC 1918.

O BGP, por si só, opera sobre uma suposição de confiança não verificada: qualquer AS pode anunciar rotas para qualquer prefixo, e um anúncio falso, por erro ou má-fé, causa um sequestro de rota. RPKI (RFC 6480) resolve essa lacuna com uma infraestrutura de chaves públicas espelhando a hierarquia real de alocação de endereços; uma ROA (RFC 6482) é uma atestação assinada de que o dono de um prefixo autorizou um ASN específico a originá-lo, e um roteador verifica essa cadeia até uma raiz confiável, o mesmo princípio da cadeia de confiança TLS descrita acima. IP spoofing, a falsificação do endereço de origem de um pacote, sustenta ataques de reflexão e amplificação; a defesa formalizada pela BCP 38 (RFC 2827), filtragem de entrada, descarta um pacote cujo endereço de origem não poderia ter vindo pela interface por onde chegou, e o uRPF (RFC 3704) implementa essa ideia consultando a tabela de roteamento, em modo estrito (a mesma interface de ida e volta) ou permissivo (só confirma que existe alguma rota). O Linux implementa isso via `net.ipv4.conf.*.rp_filter`. RPKI prova que um ASN tem autorização para anunciar um prefixo; uRPF confirma que um pacote não foi forjado no caminho, duas perguntas diferentes que soam parecidas.
