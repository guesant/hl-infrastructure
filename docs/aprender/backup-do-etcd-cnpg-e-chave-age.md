# Backup do etcd, do CloudNativePG e da chave age

Três tipos de dado num cluster Kubernetes com bancos de dados stateful e segredos cifrados pedem uma estratégia de backup própria, porque nenhum dos três é coberto pelos outros dois: o estado da própria API Kubernetes, o conteúdo de um banco relacional rodando dentro do cluster, e a chave privada que decifra os segredos do repositório GitOps. Perder qualquer um dos três sem uma cópia de recuperação é, na prática, perder tudo que depende dele, mesmo que o restante do sistema esteja intacto.

## Snapshot do etcd

O K3s, como qualquer distribuição Kubernetes que roda seu próprio datastore, guarda o estado da API (objetos, ConfigMaps, Secrets, metadados de todos os recursos) no etcd, e oferece um mecanismo nativo de snapshot desse datastore agendado automaticamente em intervalos regulares, com uma retenção configurável de quantos snapshots recentes manter. Esse snapshot é poderoso e limitado ao mesmo tempo: ele protege exatamente o estado declarado da API, mas não contém o conteúdo de volumes persistentes, nem arquivos externos ao host, nem imagens de container, então restaurar um snapshot recria os objetos Kubernetes tal como existiam naquele momento, sem recriar automaticamente os dados que esses objetos referenciam. Um snapshot que fica apenas no disco local do mesmo host não cumpre a função de backup, porque a falha mais provável de proteger contra, a perda do próprio host, destrói o snapshot junto com o original; copiar o snapshot (e, separadamente, o token de autenticação do servidor, sem o qual novos nós não conseguem se juntar a um cluster restaurado) para um destino fora do host é o que efetivamente fecha essa proteção.

Restaurar um snapshot é uma operação destrutiva por natureza: ela substitui o estado atual do datastore pelo estado congelado no momento do snapshot, e por isso normalmente é feita com o serviço parado e uma flag específica de reset do cluster. Num cluster de vários managers, restaurar acontece em um único nó, que se torna a nova fonte de verdade, enquanto os demais precisam ser removidos e reintegrados como membros novos, nunca reiniciados apontando para o datastore antigo, sob risco de dois estados divergentes coexistirem. Num cluster de nó único, essa distinção desaparece, mas a natureza destrutiva da operação permanece: não existe uma forma de "desfazer" uma restauração de snapshot além de restaurar um snapshot mais recente, e por isso um teste de restore nunca deveria acontecer contra um ambiente de produção ativo.

## Backup contínuo de um banco relacional

Um operator de banco de dados relacional dentro do cluster (o modelo mais comum para PostgreSQL é o CloudNativePG) tipicamente separa duas estratégias de backup que se complementam: o arquivamento contínuo do write-ahead log, o arquivo sequencial onde o banco registra cada mudança antes de aplicá-la aos dados, copiado para um destino externo em tempo quase real; e um backup completo agendado, uma cópia do estado inteiro do banco num ponto específico. A combinação das duas é o que permite point-in-time recovery, restaurar o banco não apenas para o momento do último backup completo, mas para qualquer instante coberto pelo WAL arquivado depois dele, o que reduz drasticamente o RPO em comparação com depender só de backups completos periódicos. Confirmar que essa proteção está funcionando não é uma inspeção única: o arquivamento de WAL pode falhar silenciosamente por uma credencial expirada ou um destino inacessível, e um backup agendado pode nunca ter rodado dentro da janela esperada, então revisar o status relatado pelo próprio operator (não apenas assumir que "está configurado, logo está funcionando") é o que efetivamente confirma a proteção. Uma falha no arquivamento de WAL tem, além do risco de backup, um efeito colateral direto: o log não arquivado se acumula no disco de dados do próprio banco, então um arquivamento parado pode virar um incidente de espaço em disco antes de virar um incidente de backup percebido. Um dump manual (`pg_dump`, ou o equivalente de outro banco relacional) é uma categoria diferente de backup, lógico em vez de físico: ele exporta o conteúdo do banco como uma sequência de comandos capazes de recriá-lo, útil para migrar dados entre versões ou mover um banco pequeno de um ambiente para outro, mas não guarda o histórico de mudanças que um WAL contínuo guarda, então não permite recuperação para um ponto específico no tempo, só para o exato momento em que o dump foi gerado.

## A chave privada que protege tudo o resto

Quando segredos num repositório GitOps são cifrados com SOPS para um conjunto de chaves públicas age (o mecanismo está descrito em [Criptografia de segredos no Git](criptografia-de-segredos-no-git.md)), a chave privada correspondente se torna o único material capaz de decifrar qualquer um desses segredos, e sua perda torna todos eles permanentemente irrecuperáveis mesmo com o repositório Git completamente intacto, porque o conteúdo cifrado não guarda nenhuma informação que permita reconstruir a chave que o protege. Isso torna essa chave qualitativamente diferente dos outros segredos do sistema: ela não é apenas mais um valor sensível, é o ponto de falha única de todos os outros. Guardar essa chave privada fora do repositório GitOps (nunca commitada, nem em um repositório privado) e fora do único host onde ela é usada em produção é a mesma lógica de isolamento de domínio de falha que se aplica a qualquer backup, aqui aplicada a uma credencial em vez de a um dado; e, quando essa chave também precisa estar disponível dentro do cluster para um controlador de sincronização decifrar segredos automaticamente, essa cópia dentro do cluster é ela mesma um dado de bootstrap que existe fora do controle do próprio GitOps, sujeito ao mesmo problema recursivo de ovo e galinha descrito em [Bootstrap e rotação de segredos](bootstrap-e-rotacao-de-segredos.md). Como qualquer backup, uma cópia da chave nunca testada é uma suposição, não uma garantia: confirmar periodicamente que a cópia guardada realmente decifra um arquivo de teste é o que distingue uma chave de recuperação real de uma cópia corrompida, incompleta, ou de uma rotação anterior que já não corresponde às chaves públicas em uso. E, ao contrário de uma senha, uma chave age comprometida não tem mecanismo de revogação: a única resposta possível é gerar um par novo e recifrar todos os arquivos protegidos pelo par antigo, o que reforça por que restringir quem tem acesso à chave privada original é mais barato do que reagir a um comprometimento depois do fato.
