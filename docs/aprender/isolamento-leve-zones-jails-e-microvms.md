# Isolamento leve: zones, jails e microVMs

Container e VM não são as duas únicas opções de isolamento. Várias tecnologias ocupam pontos intermediários entre um processo comum confinado por namespaces e cgroups e uma máquina virtual completa com hipervisor e kernel próprio, trocando força de isolamento por overhead de forma diferente da escolha binária entre esses dois extremos. Esta página percorre esse espectro, começando pelos containers de sistema, que rodam um sistema operacional completo em vez de um processo só, passando por duas formas de isolamento mais antigas que os namespaces do Linux, e terminando nas tecnologias que ficam entre um container comum e uma VM completa, como microVMs e sandboxes de processo.

## Containers de sistema: LXC, Incus e systemd-nspawn

Um container de sistema roda um init completo, `systemd` na maioria das distribuições atuais, e a partir dele quantos serviços a imagem base tiver, como `cron`, `syslog`, um servidor SSH e múltiplos daemons, exatamente como uma instalação Linux tradicional dentro de uma VM. Isso o distingue de um container de aplicação, o modelo Docker, Podman ou OCI mais comum em orquestração, desenhado para empacotar um processo só, sem init, tratado como efêmero e substituível, não como um sistema a administrar e atualizar no próprio lugar.

LXC é o conjunto de ferramentas e biblioteca que usa namespaces e cgroups diretamente para criar containers, um projeto anterior ao Docker, por volta de 2008, mantido por engenheiros que também contribuíram boa parte do trabalho original de namespaces e cgroups no kernel. LXC sozinho é uma camada de baixo nível: cria e gerencia containers via linha de comando ou API, sem um daemon central, sem API REST e sem gerenciamento de imagens ou clustering. LXD nasceu como a camada de gerenciamento sobre o LXC, um daemon com API REST, gerenciamento de imagens, armazenamento e rede abstraídos, e suporte a clustering entre hosts, desenvolvido pela Canonical.

Em agosto de 2023, depois de a Canonical exigir que todo contribuidor do LXD assinasse um acordo de licenciamento transferindo os direitos do código para a empresa e mover o projeto para fora da governança comunitária do Linux Containers, parte da equipe original do LXD criou o Incus como um fork comunitário, sob a mesma organização Linux Containers. Os dois projetos continuam ativos separadamente, LXD sob governança exclusiva da Canonical e Incus sob a organização comunitária, com boa parte dos mantenedores históricos do LXD hoje concentrados no Incus; confirme o estado atual de cada um diretamente nas fontes oficiais antes de adotar qualquer um dos dois, já que essa divisão é relativamente recente e pode evoluir.

`systemd-nspawn` é o gerenciador de containers incluído no próprio `systemd`, disponível por padrão em qualquer distribuição que já use `systemd` como init, sem instalar nenhum pacote adicional. Ele inicializa um container leve a partir de uma árvore de diretórios ou imagem, rodando um init completo dentro do namespace criado, e `machinectl`, também parte do `systemd`, gerencia esses containers depois de iniciados. É a opção mais direta para testar rapidamente uma imagem de outra distribuição, ou para depurar um ambiente isolado, sem depender de LXC, Incus ou de uma VM completa.

A diferença prática para um container de aplicação está em como cada um é administrado. Um container de aplicação é construído para ser substituído, não atualizado: uma nova versão da imagem substitui o container inteiro, o estado que precisa sobreviver fica em um volume externo, e orquestradores como o Kubernetes tratam a unidade como descartável. Um container de sistema é administrado como uma VM leve, com pacotes atualizados no próprio lugar dentro dele, uma identidade persistente e configuração acumulada ao longo do tempo, sem que exista, nem faça sentido existir, uma imagem versionada e imutável da forma como uma imagem OCI funciona. Containers de sistema se justificam para replicar rapidamente um ambiente de teste de uma distribuição completa sem o custo de boot e memória de uma VM, para rodar uma aplicação legada que já assume múltiplos serviços coexistindo sob um único init, ou para hospedar múltiplos ambientes isolados em um único host físico como alternativa mais leve a várias VMs completas quando todos os ambientes já rodam Linux.

## Solaris Zones e BSD Jails: isolamento antes dos namespaces do Linux

FreeBSD Jails e Solaris Zones resolveram, cada um à sua forma, o mesmo problema central que os namespaces do Linux resolvem hoje, isolar múltiplos ambientes rodando sobre um único kernel, anos antes do Linux ter uma resposta equivalente. Entender os dois ajuda a ver o que é decisão de design específica do Linux e o que é um problema mais antigo e mais geral de sistemas operacionais Unix.

O mecanismo de jail foi desenvolvido em 1999 por Poul-Henning Kamp, encomendado por um provedor de hospedagem compartilhada que precisava separar os ambientes de clientes diferentes no mesmo servidor físico, e entrou no FreeBSD 4.0, lançado em 14 de março de 2000. Isso é anterior ao primeiro namespace do Linux, o mount namespace incorporado ao kernel 2.4.19 em 2002, por pelo menos dois anos, e décadas anterior aos oito tipos de namespace que o Linux tem hoje. Um jail parte do conceito de `chroot`, que só restringe acesso ao sistema de arquivos, e o expande, virtualizando três recursos ao mesmo tempo: o sistema de arquivos, o conjunto de usuários e a pilha de rede. Um processo comprometido dentro de um jail encontra uma superfície de escape bem menor que um processo dentro de um `chroot` simples, porque as três dimensões de isolamento precisam ser contornadas juntas, não só uma.

Solaris Zones foi introduzida no Solaris 10, em 2005. O modelo se organiza em torno de uma zona global, a instância do sistema operacional rodando diretamente sobre o hardware com controle administrativo sobre todas as demais, e uma ou mais zonas não globais, cada uma uma instância isolada dedicada a um conjunto específico de aplicações. Segundo a documentação oficial da Oracle, o isolamento de processos entre zonas é forte o suficiente para que mesmo um processo rodando com credenciais de root não consiga ver ou afetar atividade em outras zonas, uma garantia mais explícita do que o modelo Linux costuma declarar por padrão, onde root dentro de um namespace ainda depende de user namespaces configurados corretamente para ter a mesma garantia. Uma variante, a kernel zone, roda seu próprio kernel separado, podendo inclusive rodar uma versão diferente do Solaris da zona global, o que a aproxima conceitualmente mais do modelo de VM e hipervisor do que do modelo de container com kernel compartilhado.

A semelhança central entre jails, zones e o modelo Linux é a mesma nos três: um único kernel compartilhado, com um mecanismo do próprio sistema operacional decidindo o que cada ambiente isolado consegue ver e afetar, sem a camada de hipervisor de uma VM. A diferença estrutural mais importante está em como cada modelo compõe esse isolamento: um jail ou uma zona não kernel empacota sistema de arquivos, rede e usuários como uma única unidade, ativada ou desativada em conjunto, sem a opção de isolar só a rede de um processo enquanto ele continua vendo o sistema de arquivos do host, por exemplo. O modelo Linux trata cada dimensão de isolamento como um tipo de namespace independente, que um processo pode adotar seletivamente, uma composição mais granular que o modelo monolítico de jail ou zone não oferece da mesma forma.

Jails e Zones provaram em produção, anos antes do Linux ter um mecanismo equivalente completo, que isolar múltiplos ambientes sobre um único kernel compartilhado era viável e seguro o suficiente para hospedagem multi-cliente. O caminho do Linux até os namespaces atuais foi incremental, começando pelo mount namespace em 2002 e só completando o conjunto com user namespaces em 2013; nesse intervalo, projetos como o OpenVZ, um patch de kernel Linux fora da árvore principal, já ofereciam isolamento parecido ao de um jail ou zone antes que o kernel principal tivesse suporte nativo. LXC nasceu diretamente sobre os namespaces nativos assim que ficaram disponíveis, mas o problema que ele resolve, e o vocabulário usado para descrevê-lo, já estava bem estabelecido pelos sistemas Unix que vieram antes.

## MicroVMs e sandboxes de processo: o espectro entre container e VM

Além dos modelos acima, uma segunda faixa de tecnologias ocupa o espaço entre um container comum e uma VM completa, cada uma adicionando uma camada de contenção a mais, e um custo de overhead a mais, na direção de uma VM.

Firecracker é um monitor de máquina virtual de código aberto criado pela AWS para os serviços Lambda e Fargate, construído sobre KVM. Ele reduz o conjunto de dispositivos emulados a apenas cinco, entre eles dispositivos virtio de rede e bloco, o que reduz tanto a superfície de ataque quanto o overhead de cada instância; a documentação oficial cita inicialização em torno de 125 milissegundos e overhead de memória abaixo de 5 mebibytes por microVM, uma ordem de grandeza mais próxima de um container do que de uma VM tradicional, mantendo o isolamento de ter um kernel convidado próprio por trás do KVM.

gVisor, criado pelo Google, segue um caminho diferente: em vez de rodar um kernel convidado separado sobre um hipervisor, ele intercepta as chamadas de sistema do processo confinado e as atende por conta própria, através de um componente chamado Sentry, um kernel de aplicação rodando em espaço de usuário. As chamadas não chegam ao kernel real do host; um componente separado, o Gofer, medeia o acesso ao sistema de arquivos via um protocolo próprio. O runtime `runsc` integra tudo isso ao Docker e ao Kubernetes como qualquer outro runtime OCI, e o resultado é uma camada de isolamento mais forte que namespaces e seccomp sozinhos, sem o overhead fixo de uma VM completa, ao custo de reimplementar, e não repassar, a superfície de chamadas de sistema que a aplicação usa, o que pode expor incompatibilidades com chamadas menos comuns.

`bubblewrap` fica mais próximo do lado do container comum: é um sandbox leve baseado nos mesmos namespaces do Linux, sem daemon nem formato de imagem, usando exatamente os mesmos mecanismos de isolamento já usados por qualquer container, só que declarados por linha de comando em vez de por um runtime completo. Kata Containers, por outro lado, inverte a lógica de um container comum: em vez de compartilhar o kernel do host, cada container ou Pod roda dentro de sua própria VM leve, usando QEMU ou o próprio Firecracker como monitor de máquina virtual por trás. O runtime `kata-runtime` é compatível com a especificação OCI, funcionando como substituto direto do runtime padrão para quem quer o isolamento de kernel próprio por instância mantendo a interface e as ferramentas já usadas para operar containers; o custo dessa troca aparece tanto em tempo de início, algo entre 100 e 300 milissegundos contra a faixa de dezenas de milissegundos de um container comum, quanto em um piso de memória bem mais alto por instância.
