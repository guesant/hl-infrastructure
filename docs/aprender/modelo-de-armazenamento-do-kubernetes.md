# Modelo de armazenamento do Kubernetes

Um Pod é substituível, o Kubernetes pode recriá-lo em outro nó a qualquer momento; os dados que precisam sobreviver a essa substituição não podem viver no filesystem do container, precisam de um recurso independente do ciclo de vida do Pod. Três objetos resolvem isso por indireção. Um `PersistentVolumeClaim` (PVC) é a solicitação de uma aplicação, quanto espaço, qual modo de acesso, opcionalmente qual `StorageClass`; não descreve armazenamento físico, descreve uma necessidade. Uma `StorageClass` identifica um provisionador (Longhorn, um driver de nuvem, NFS) e os parâmetros que ele deve usar; pode ser marcada como padrão do cluster, e sem uma classe padrão um PVC sem `storageClassName` fica `Pending` indefinidamente. Um `PersistentVolume` (PV) representa o armazenamento provisionado de fato, criado automaticamente pelo provisionador quando um PVC é aceito, ou registrado manualmente em cenários estáticos; o Kubernetes associa (`bind`) um PV a um PVC compatível, e a partir daí o Pod monta o PVC, resolvendo para o PV correspondente. Essa indireção existe para que o manifesto do PVC não precise conhecer detalhes do backend: o mesmo manifesto funciona com Longhorn, um driver de nuvem ou NFS, só a `StorageClass` referenciada muda. Todo dado que precisa sobreviver à recriação de um Pod (bancos de dados, filas com persistência, arquivos enviados por usuários) deve usar um PVC; dados reconstruíveis a partir de outra fonte não precisam, e um PVC desnecessário só adiciona complexidade operacional de backup e capacidade sem necessidade real.

## Modos de acesso e política de reclamação

Um PVC mal configurado costuma falhar de duas formas: fica `Pending` porque nenhum PV compatível existe, ou é vinculado a um PV cujo modo de acesso não atende à aplicação. `ReadWriteOnce` (RWO) permite um único nó montar para leitura e escrita; `ReadOnlyMany` (ROX) permite vários nós montarem só para leitura; `ReadWriteMany` (RWX) permite vários nós montarem para leitura e escrita simultaneamente; `ReadWriteOncePod` restringe a um único Pod, não apenas um nó. Nem todo provisionador suporta todos os modos, e RWX geralmente tem overhead maior; não usar RWX como padrão "por segurança" quando a aplicação só precisa de RWO evita esse custo desnecessário. A política de reclamação decide o que acontece com o PV quando o PVC associado é excluído: `Delete` remove o PV e os dados junto com o PVC, a política padrão da maioria dos provisionadores dinâmicos; `Retain` mantém o PV em estado `Released` depois da exclusão, exigindo limpeza manual antes de reutilizar, uma escolha sensata para bancos de dados e qualquer volume cuja perda acidental seria grave, já que evita exclusão por um `kubectl delete pvc` equivocado, ao custo de exigir revisão periódica de PVs `Released`, que não aparecem como problema porque o PVC já não existe mais.

## Vincular um PVC novo a um volume já existente

O fluxo comum é o inverso, um PVC pedindo um volume novo que um provisionador cria sob demanda, mas o caminho contrário também é um recurso real do modelo: declarar um `PersistentVolume` manualmente, apontando para um volume que já existe fisicamente (um volume restaurado de um backup, por exemplo, cujos dados já estão lá, só sem um objeto Kubernetes que o represente ainda), e deixar um PVC novo se vincular a esse PV específico em vez de disparar a criação de um volume vazio. Isso é o que permite recuperar um volume restaurado fora do fluxo normal do provisionador dinâmico: o PV declarado manualmente aponta para o identificador real do volume já restaurado, e o PVC que o reivindica se comporta, dali em diante, como qualquer outro PVC comum para a aplicação que o monta, sem que ela precise saber que os dados chegaram por um caminho fora do padrão.
