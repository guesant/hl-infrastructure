# Bancos não relacionais: chave-valor e documento

Um banco de dados relacional como o PostgreSQL, já coberto em [Backup do etcd, do CloudNativePG e da chave age](backup-do-etcd-cnpg-e-chave-age.md), organiza dados em tabelas com um schema definido antecipadamente e relações declaradas entre elas, garantidas por restrições de integridade que o próprio banco aplica. Esse modelo não é a única forma de guardar dado persistente, e a família de bancos genericamente chamada NoSQL cobre alternativas que trocam alguma dessas garantias por outro tipo de vantagem, geralmente performance para um padrão de acesso específico ou flexibilidade de schema. Nenhuma dessas alternativas é uma substituta genérica de um banco relacional; cada uma resolve bem um formato de dado e um padrão de acesso específicos, e mal quase todo o resto.

## Banco chave-valor: acesso rápido e simples

Um banco de dados chave-valor, do qual o Redis é o exemplo mais difundido, armazena e recupera um valor a partir de uma chave, sem consultas relacionais nem junção entre tabelas: a operação central é "guarde este valor sob esta chave" e "devolva o valor guardado sob esta chave", ambas extremamente rápidas por não exigirem nenhum plano de consulta a calcular. O Redis especificamente mantém os dados primariamente em memória, o que explica sua velocidade característica, mas também significa que o volume de dados guardado é limitado pela memória disponível, diferente de um banco em disco cuja capacidade escala com o espaço de armazenamento. Isso o torna adequado para cache (guardar temporariamente o resultado de uma consulta cara para não recalculá-la a cada requisição), sessão de usuário, contadores em tempo real e filas simples, casos onde o acesso é sempre por uma chave conhecida e a durabilidade absoluta de cada valor individual é menos crítica que a velocidade de acesso; é inadequado para dados que exigem consulta por qualquer campo além da chave, ou para relatórios que cruzam informação de múltiplas entidades.

## Banco de documento: schema flexível por registro

Um banco de documento, do qual MongoDB é o exemplo mais citado, guarda cada registro como um documento (tipicamente JSON ou um formato binário equivalente) que pode ter uma estrutura diferente de outro documento na mesma coleção, sem um schema único imposto pelo banco a toda a coleção. Isso favorece um modelo de dado que muda de formato com frequência ao longo do tempo, ou onde entidades do mesmo tipo genuinamente têm atributos diferentes entre si (um catálogo de produtos onde categorias diferentes têm campos completamente diferentes, por exemplo), sem exigir uma migração de schema formal a cada mudança de formato, ao custo de perder as garantias de integridade que um schema relacional aplicado uniformemente oferece: nada impede, por padrão, dois documentos supostamente do mesmo tipo terem campos com nomes ou tipos inconsistentes entre si, uma inconsistência que só um schema explicitamente validado (que a maioria desses bancos também oferece como opção, não como padrão obrigatório) preveniria.

## O que se perde ao sair do modelo relacional

A vantagem de performance ou de flexibilidade de um banco não relacional normalmente vem à custa de uma ou mais garantias que um banco relacional oferece por padrão: uma transação atômica cruzando múltiplas entidades diferentes (garantir que duas escritas relacionadas aconteçam as duas ou nenhuma, mesmo entre documentos ou chaves diferentes) costuma ter suporte mais limitado ou inexistente; uma junção eficiente entre dois conjuntos de dados relacionados, o ponto forte central de um banco relacional, não existe da mesma forma, forçando o modelo de dado a duplicar informação entre documentos para evitar precisar juntar dados de coleções diferentes numa consulta; e a consistência entre réplicas, quando o banco é distribuído entre múltiplos nós, frequentemente segue um modelo de consistência eventual (uma escrita pode não estar imediatamente visível para uma leitura em outra réplica, refletindo com um atraso curto) em vez da consistência imediata que um banco relacional tradicional de nó único garante por padrão.

## Escolher o banco pelo padrão de acesso, não pela moda

A decisão entre um banco relacional e um não relacional (ou entre um banco chave-valor e um de documento) deveria partir do padrão de acesso real que a aplicação precisa, não de uma preferência genérica por "NoSQL é mais moderno" ou o inverso. Um sistema que precisa de relatórios cruzando múltiplas entidades, transações atômicas entre elas, e um schema estável ao longo do tempo tem no modelo relacional a ferramenta certa; um sistema que só precisa de acesso rápido por chave, sem relação nenhuma entre os valores guardados, ganha pouco ou nada adotando um banco relacional para esse caso específico. Nada impede, e é comum na prática, um mesmo sistema usar mais de um tipo de banco ao mesmo tempo, cada um resolvendo a parte do problema para a qual é o modelo certo, em vez de forçar um único banco a cobrir bem todos os padrões de acesso do sistema inteiro.
