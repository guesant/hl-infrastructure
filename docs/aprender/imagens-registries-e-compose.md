# Imagens, registries e Compose

`Containerfile` é o nome adotado por ferramentas neutras de fornecedor, como Podman e Buildah, para o mesmo formato de instruções (`FROM`, `RUN`, `COPY`, `ENTRYPOINT`) que o `Dockerfile` do Docker popularizou; `podman build` e `buildah bud` procuram um `Containerfile` primeiro e caem para `Dockerfile` como alternativa, então um projeto pode manter só um dos dois nomes sem perder compatibilidade. Um ponto frequentemente mal entendido: a sintaxe de instruções não é parte da OCI Image Spec, descrita em [especificações OCI e a pilha de runtimes](especificacoes-oci-e-pilha-de-runtimes.md). A OCI padroniza o formato do resultado de um build, não a linguagem usada para descrever como chegar até esse resultado; `Dockerfile`/`Containerfile` é um padrão de fato, interpretado por qualquer motor de build compatível.

O contexto de build é o conjunto de arquivos, tipicamente todo o diretório indicado ao final do comando, enviado ao motor de build antes da primeira instrução ser processada; instruções `COPY`/`ADD` só conseguem referenciar arquivos que já fazem parte desse contexto. Um `.dockerignore` exclui caminhos dessa transferência, o que importa por performance e por risco de vazamento: um arquivo sensível dentro do diretório do build, como uma chave privada esquecida, pode acabar dentro do contexto e, de lá, dentro de uma camada da imagem, caso uma instrução copie um diretório inteiro sem excluí-lo explicitamente. BuildKit é o motor usado pelo Docker Engine atual, processando estágios de um `Dockerfile` multi-stage em paralelo quando não há dependência entre eles, com cache mais granular por instrução e suporte a segredos de build (`--secret`) que ficam disponíveis durante uma instrução `RUN` específica sem serem persistidos em nenhuma camada final, ao contrário de passar um segredo como `ARG`/`ENV`, que fica gravado no histórico da imagem. Buildah, do mesmo ecossistema do Podman, também permite construir uma imagem de forma imperativa, comando a comando (`buildah from`, `buildah run`, `buildah copy`, `buildah commit`), sem exigir arquivo de instruções, mais verboso para o caso comum mas mais programável para pipelines que geram a sequência de build dinamicamente. Nenhum dos dois motores determina se a imagem resultante funciona com Docker Engine, Podman, containerd ou qualquer outro consumidor compatível com OCI.

Skopeo opera em imagens e manifestos diretamente, sem exigir um daemon nem baixar a imagem para o armazenamento local antes de agir, o que o torna a ferramenta certa para mover ou inspecionar imagens sem executá-las: `skopeo inspect docker://docker.io/library/nginx:1.27` confere metadados sem baixar nada, e `skopeo copy docker://origem.example.com/app:1.0 docker://destino.example.com/app:1.0` copia diretamente entre dois registries. Os prefixos de transporte (`docker://` para um registry, `containers-storage:` para o armazenamento local, `oci:` para um layout OCI em disco, `dir:` para um diretório simples) definem origem e destino de cada operação, e `skopeo copy` pode converter entre alguns deles na mesma operação, útil também para extrair uma imagem para um diretório local sem nenhum runtime de container envolvido.

## Tags, digests e por que a reprodutibilidade importa

Uma tag explícita, como `api:2.4.1`, comunica a versão mas pode ser republicada se o registry permitir; uma tag flutuante, como `latest` ou `stable`, pode apontar para conteúdos diferentes sem nenhuma alteração no manifesto que a referencia. Um digest, como `api@sha256:...`, identifica o conteúdo de forma imutável por hash: quando tag e digest aparecem juntos, o runtime usa o digest para selecionar o conteúdo, e a tag serve só para relacionar a imagem às notas da release. `latest`, `stable`, nomes de canal e tags de branch são flutuantes mesmo quando parecem estáveis, e uma tag numérica não é imutável por definição, a garantia depende da política do registry e do processo de publicação. Fixar um digest garante identidade e integridade do conteúdo recuperado; não comprova quem o produziu, se o processo de build era confiável, nem se a imagem está livre de vulnerabilidades. Este cluster resolve o problema de manter esse digest atualizado no estado desejado do Git com o Kargo, documentado em [rollout de imagens](../arquitetura/rollout-de-imagens.md); o que importa reter aqui é só o conceito, tag mutável referenciando o quê versus digest imutável identificando o quê, não o mecanismo de reconciliação em si.

## Registries: dois tipos de produto, não uma lista de marcas

A primeira distinção importante não é entre marcas de registry, é entre dois tipos de produto. Um **registry OCI dedicado** tem uma função só, armazenar e distribuir imagens no formato OCI, implementando o protocolo Distribution Spec. Um **gerenciador universal de artefatos** também guarda imagens OCI, mas ao lado de pacotes npm, Maven, PyPI, charts Helm e arquivos genéricos, atrás de um único sistema de permissões. Um registry dedicado é mais simples de operar quando o único problema é distribuir imagens; um gerenciador universal se paga quando a organização já precisa resolver o mesmo problema para vários formatos de pacote ao mesmo tempo. Entre as opções self-hosted, Harbor resolve autenticação, autorização, UI, scanning e replicação prontos, ao custo de operar mais um sistema com mais partes móveis; CNCF Distribution e Zot entregam só o protocolo de distribuição, deixando cada uma dessas decisões para quem opera. SaaS integrados a uma forge, como o GitHub Container Registry, reduzem a decisão a usar o que já está disponível na plataforma onde o código já está hospedado; este cluster publica sua própria imagem em `ghcr.io/guesant/blog` exatamente por esse motivo, sem operar registry próprio.

## A Compose Specification

A Compose Specification é uma especificação aberta, não controlada por um único fornecedor, que define o schema de um arquivo `compose.yml`: como declarar serviços, redes e volumes para descrever uma aplicação multi-container. Docker Compose e Podman Compose são duas implementações independentes dessa mesma spec, o mesmo padrão de camada neutra já visto na OCI: a spec define o formato, cada ferramenta decide como executá-lo. Versões antigas exigiam um campo `version:` no topo do arquivo; a spec eliminou essa exigência e padronizou `compose.yaml`/`compose.yml` como nome canônico, embora `docker-compose.yml` continue funcionando por compatibilidade retroativa.

Um arquivo `compose.yml` declara um projeto nomeado contendo um ou mais serviços, redes e volumes nomeados; subir um projeto sem nenhuma rede declarada explicitamente cria uma rede bridge exclusiva desse projeto, e cada serviço fica alcançável pelos demais através de um DNS interno que resolve o nome do serviço para o IP do container correspondente, sem precisar de IPs fixos. Um serviço `api` com `depends_on: [db]` consegue se conectar a `db:5432` diretamente porque a resolução de nome já resolve `db` dentro da rede daquele projeto específico; um segundo projeto com um serviço também chamado `db` não colide com o primeiro, porque cada projeto tem sua própria rede isolada por padrão. Docker Compose v2 é um plugin do Docker CLI que traduz o arquivo nas chamadas de API do Docker Engine equivalentes; `podman compose` é um wrapper fino em torno de um provedor externo, tipicamente `docker-compose` ou o `podman-compose` mantido pela comunidade, que por sua vez fala com o Podman em vez do Docker Engine.

A spec aceita combinar mais de um arquivo numa única execução (`-f compose.yml -f compose.override.yml`), útil para manter uma definição base e sobrepor só o que muda entre ambientes; valores escalares do arquivo mais recente substituem os do anterior, enquanto a maioria dos campos de lista, como `cap_add` ou `ports`, é concatenada em vez de substituída inteiramente. A spec reserva o prefixo `x-` para extensões específicas de uma ferramenta, ignoradas silenciosamente por implementações que não as reconhecem; campos padrão também podem ter interpretação específica por implementação, como `userns_mode`, cujo comportamento rootless por trás depende de qual ferramenta está interpretando o arquivo.
