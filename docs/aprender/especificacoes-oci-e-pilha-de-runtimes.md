# Especificações OCI e a pilha de runtimes

OCI (Open Container Initiative) é uma estrutura de governança sob a Linux Foundation que mantém três especificações independentes entre si: Image, Distribution e Runtime. "Compatível com OCI" não é uma propriedade binária de uma ferramenta; é preciso perguntar com qual das três, porque uma ferramenta pode implementar uma sem implementar as outras. A OCI foi fundada em 2015, com o Docker e outras empresas do setor como membros fundadores, para formalizar como especificações abertas o que já era, na prática, o formato de imagem e o modelo de execução do Docker, permitindo que "uma imagem OCI" ou "um runtime OCI" fossem tratados de forma intercambiável por qualquer ferramenta compatível, não só pelo Docker.

A **Image Specification** padroniza o conteúdo de uma imagem: um conjunto de camadas, cada uma um diff do sistema de arquivos, um arquivo de configuração descrevendo variáveis de ambiente, comando de entrada e usuário padrão, e um manifesto que amarra camadas e configuração numa unidade identificável por digest; para imagens multi-plataforma, um índice de manifestos agrupa um manifesto por arquitetura sob um único digest de nível superior. A spec não diz nada sobre como a imagem chega a um host nem como é executada, só o que ela contém. A **Distribution Specification** padroniza a API HTTP que um registry expõe para enviar e receber blobs e manifestos; qualquer cliente compatível, `docker pull`, `podman pull`, `skopeo`, consegue falar com qualquer registry compatível, independentemente do produto por trás de cada lado, o que permite migrar de um registry para outro sem trocar o cliente. A **Runtime Specification** padroniza um bundle: um diretório com o filesystem raiz já extraído e um arquivo `config.json` descrevendo exatamente como o processo deve ser executado, na prática uma descrição declarativa dos mesmos mecanismos cobertos em [processo, namespaces e usuários](processo-namespaces-e-usuarios.md) e em [cgroups, capabilities e isolamento de filesystem](cgroups-capabilities-e-filesystem.md): quais namespaces criar, quais mounts aplicar, quais capabilities conceder. Um runtime de baixo nível como `runc` ou `crun` lê esse `config.json` e faz exatamente as chamadas de sistema (`clone` com as flags `CLONE_NEW*`, `pivot_root`, escrita nos arquivos de cgroup) que transformam essa descrição num processo confinado de verdade.

## A pilha entre `docker run` e o processo confinado

Docker, Podman, containerd e runc não são alternativas concorrentes: são camadas diferentes da mesma pilha. Um **engine** (Docker Engine, Podman) é a ferramenta com que uma pessoa interage, gerenciando imagens, redes, volumes e a experiência de linha de comando. Um **runtime de alto nível** (containerd, CRI-O) gerencia o ciclo de vida de containers individuais: busca a imagem, prepara o filesystem, entrega a execução propriamente dita a uma camada mais baixa. Um **shim** desacopla o processo do container do processo do runtime que o criou, porque um runtime de baixo nível como `runc` é de vida curta, criado para configurar o container e depois terminar; algum processo precisa continuar existindo como pai do processo do container depois disso, e se o runtime de alto nível reiniciar ou travar, os containers em execução não podem morrer junto. `containerd-shim` cumpre esse papel para o `containerd`; no Podman, `conmon` cumpre um papel equivalente, com implementação própria, sem relação de código com o shim do containerd. Um **runtime de baixo nível** (`runc`, `crun`) é quem finalmente faz as chamadas de sistema que a Runtime Spec descreve.

`containerd` nasceu como parte do Docker Engine e foi extraído como projeto independente, hoje graduado pela CNCF; gerencia puxar a imagem, preparar camadas via snapshotter, invocar o runtime de baixo nível e supervisionar o processo resultante, mas não tem CLI voltada ao usuário final. CRI-O foi criado especificamente para implementar a CRI (Container Runtime Interface) do Kubernetes, sem nenhum outro propósito, deliberadamente mais enxuto que o containerd porque resolve só o subconjunto que o kubelet precisa. `runc`, escrito em Go, é a implementação de referência da Runtime Spec, mantida pela própria OCI e originada do código do Docker Engine. `crun`, escrito em C, é uma implementação alternativa da mesma spec, com inicialização mais rápida e menor consumo de memória, especialmente perceptível com muitos containers de vida curta; Podman e CRI-O costumam usar `crun` como padrão em instalações recentes, mas ambos aceitam qualquer runtime de baixo nível compatível.

CRI é a API gRPC que o `kubelet` usa para pedir a criação, o encerramento e a inspeção de containers a um runtime, sem precisar conhecer detalhes específicos de qual runtime está do outro lado; é isso que permite ao Kubernetes trocar de `containerd` para `CRI-O` sem alterar o comportamento observável de um Pod, e o motivo de o Kubernetes não depender mais do Docker Engine diretamente, contornando inteiramente a camada de engine, que existe para atender um humano na linha de comando, uma necessidade que o kubelet não tem. K3s empacota `containerd` e o configura como runtime padrão atendendo ao kubelet via CRI; veja [arquitetura do K3s](k3s.md) para como isso se encaixa no restante dos componentes.

## Docker vs. Podman: critérios de escolha

Docker Engine e Podman produzem o mesmo resultado final, um processo confinado a partir de uma imagem OCI, por arquiteturas diferentes. Docker Engine (`dockerd`) é um daemon sempre em execução, gerenciando imagens, redes e volumes, delegando a execução de cada container ao `containerd`; é esse daemon que o socket do Docker expõe, e montar esse socket em qualquer execução automatizada equivale a conceder acesso administrativo ao host, porque qualquer processo com acesso de escrita a ele pode pedir um container montando qualquer caminho do host e rodando como root. Podman não tem daemon: cada comando roda, executa a operação e termina, usando sua própria biblioteca (`libpod`) para gerenciar containers diretamente, com um processo leve chamado `conmon` fazendo o papel de supervisor por container, sem passar por `containerd` nem por um shim equivalente. Podman roda rootless por padrão, sem configuração adicional; Docker também suporta rootless, mas como um modo de instalação separado (`dockerd-rootless`) que substitui a instalação padrão, uma decisão deliberada, não o caminho de menor esforço. O mapeamento de UID/GID por trás de cada modo está detalhado em [processo, namespaces e usuários](processo-namespaces-e-usuarios.md#user-namespaces-o-que-root-dentro-do-container-significa).

Um daemon central significa mais um processo para manter atualizado e monitorado, mas também um ponto único por onde toda a atividade de containers do host passa, o que simplifica auditoria centralizada; sem daemon, cada `podman run` é só mais um processo filho de quem o invocou, sem serviço para reiniciar separadamente, mas também sem um ponto central único para auditar toda a atividade de uma vez. Podman foi desenhado deliberadamente para aceitar a mesma sintaxe de comando do `docker`, o que torna `alias docker=podman` uma prática comum e geralmente segura para uso interativo; a compatibilidade não é absoluta, recursos específicos do ecossistema de plugins do Docker ou comportamentos particulares do Compose v2 podem não ter equivalente 1:1. Times já padronizados no ecossistema Docker, com imagens de terceiros assumindo `docker` ou integrações de CI que esperam o socket disponível, tendem a ter menos atrito seguindo com Docker Engine; ambientes onde rodar sem daemon root é requisito de segurança, ou onde a integração nativa com `systemd` (`podman generate systemd`, ou Quadlet em versões recentes) é desejada sem trabalho manual, tendem a se beneficiar mais do Podman. O que não muda com a escolha: as duas consomem imagens OCI e falam com registries da mesma forma, e no fim da pilha ambas terminam invocando o mesmo tipo de runtime de baixo nível, então o isolamento de kernel que um container recebe não muda pela escolha do engine, só a forma como esse engine chega até lá.
